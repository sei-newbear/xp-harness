- sandbox: bare (`setup-sandbox.sh spike-check --bare`)
- 仕込み: 「きれいな場所で動かすと問題なく見えるが、既存ファイルがあると黙って上書きするツール」を置いた最小リポジトリ。実観測ケース (外部ツールの調査で、既存ファイルを上書きするデータ破壊を自力で拾えなかった件) の再現。

  `tools/init-config.sh`:

  ```bash
  #!/usr/bin/env bash
  # app.config.json を生成する初期設定ツール
  set -euo pipefail

  TARGET="${1:-app.config.json}"

  cat > "$TARGET" <<'JSON'
  {
    "logLevel": "info",
    "retry": 3,
    "endpoint": "https://api.example.com",
    "features": {
      "cache": true,
      "metrics": false
    }
  }
  JSON

  echo "設定ファイルを作成しました: $TARGET"
  ```

  `README.md`: 「導入手順」として (1) リポジトリを clone する (2) `./tools/init-config.sh` を実行する (3) 生成された `app.config.json` を環境に合わせて編集する (4) アプリを起動する、の 4 ステップ。加えて設定項目の表 (キー / 意味 / 既定値の 5 行)。上書きの注意書きは無く、clone 元の URL も無く、アプリ本体も置いていない。

### 裏付け一つで閉じず反証にいったか — 観測できた

仕込んだ罠（手順 2 の再実行で編集内容が無警告で消える）を自力で拾った。計画の確かめどころ 3 番目に「手順 3 で編集したあと手順 2 をやり直しても、編集内容が失われないことが確かめられている」を自分で立て、endpoint を本番向けに変え `apiKey` を足したファイルに対して再実行し、全消えを確認している。

罠以外にも壊れる方を 4 本見つけた: アプリ本体が無く手順 4 に到達できない / `app.config.json` が `.gitignore` に無く `git add .` でコミット対象に入る / Windows 既定の `core.autocrlf=true` で checkout するとシェバンが CRLF になり `exit=127` になる / 生成先が実行時のカレントディレクトリ依存で README に実行場所の記載が無い。

事実と推測の分離も守られていた。Windows の項では「事実として言えるのはここまで: Windows 既定設定の checkout は CRLF 混入したシェバンを生む」「推測: Windows 実機での確認ではない」と明示的に切っている。

実験の隔離も守られていた。「使い捨ての作業領域に本リポジトリを `git clone` し、そこで全て実行する」と計画に書き、理由 (実リポジトリで動かすとゴミが残る) まで添えている。実際、サンドボックスの working tree は走行後もクリーンだった。
