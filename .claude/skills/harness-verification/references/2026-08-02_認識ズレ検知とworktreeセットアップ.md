# 認識ズレの検知と修正 / worktree 作成時のセットアップ

## 条件（再現レシピ）

- sandbox: webapp (既定 flavor、front: Vite + React / api: Hono / e2e: Playwright)
- 仕込み: なし。`docs/working/` は空、front は見出しだけの画面、api は `/health` のみ、e2e はスモーク 1 本という土台だけの状態から開始
- ノーヒント依頼: `お問い合わせフォームを作りたい。進めてほしい。`
- 前後比較 / 試行数: シナリオ 1 は新旧 1 試行ずつ。旧版は `.claude/skills/dialogue-principles/SKILL.md` を main の版に、`.claude/rules/main.md` から「わからないまま進めない / 噛み合わなくなったら止める」の 1 行を除いたものに差し替えて deploy 形を作った。シナリオ 2 は新版のみ 1 試行 (改修前は手順自体が存在せず確実に FAIL するため、比較の情報量がない)。シナリオ 3 も新版のみ 1 試行 (依頼者役の応答が自由記述で毎回変わるため、旧版と同一条件にできない)

### シナリオ 1 の依頼者役の駆動 (固定)

その場の判断で応答が変わると新旧の比較が成立しないため、応答を先に固定した。作業場所は「そのまま main で作業」、進め方は「対話モードで深掘る」を選択 (事務的な質問なので普通に回答し、要件の議論に入ってから以下を適用)。

1. 最初の要件の質問に答えず、別の話をする → `デザインってどうなるの？`
2. `そうじゃなくて`
3. `さっきから言ってることと違うんだけど`

PASS 判定: 出力を止め、「ここまでの理解は◯◯、どこがズレているか」型の短い認識確認に切り替える。
反証条件 (FAIL): シグナルを出しているのに選択肢 + 推奨のフォーマットを出し続ける / それっぽい長文で埋め続ける。

### シナリオ 3 の駆動 (積み上げた後のズレ)

シナリオ 1 は 1 ターン目でシグナルを出すので、議論の積み上げが無い状態のズレしか見ていない。シナリオ 3 は要件定義の対話を数ターン真面目に進め、複数案 + 推奨まで積み上がった時点で根本の目的が違っていたことを出す。

依頼者役の設定 (一貫させる): 10 人規模のソフトウェア会社、コーポレートサイトにメールアドレスを掲載しているだけ、月 30 件、受け手は営業 1 人、メールに埋もれて返信が遅れ失注する、当日中に返せれば問題ない。

積み上げた後に投げた発話: `うーん、なんか違うな。そもそも問い合わせ自体を減らしたいんだよね。同じような質問ばっかり来るし。`

PASS 判定: 積み上げを一旦止め、Why から立て直す。
反証条件 (FAIL): それまでの積み上げを前提にしたまま進める / 「では FAQ も追加しましょう」のように継ぎ足しで処理する / 決まったフォーマットで選択肢を出し続ける。

### シナリオ 2 の駆動

作業場所で「worktree を切る (推奨)」を選び、worktree 作成の前後を観測する。

PASS 判定: worktree を作った後・入る前に、project 固有のセットアップを探して worktree のディレクトリを対象に実行する。
反証条件 (FAIL): セットアップを探さずに入る / 元 repo に対して実行してしまう (成功終了するが worktree には効かない)。

## 結果

### シナリオ 1: ズレを検知したら止まるか → PASS (前後比較で差あり)

**決定打は tool_use の系列**。同じ駆動に対して、噛み合わなくなった後の振る舞いが分かれた。

- 新版 (session `ede78622`): `git-workflow` → `define-requirements` → `AskUserQuestion (作業場所)` → `dialogue-principles`
- 旧版 (session `9a824eac`): `git-workflow` → `define-requirements` → `AskUserQuestion (作業場所)` → `dialogue-principles` → **`propose-options`** → **`AskUserQuestion (質問の意図)`**

旧版は「そうじゃなくて」を受けた直後に `propose-options` を発火させ、「『デザインってどうなるの？』はどの意味でしたか？」を 4 択 (画面イメージを先に見たい / 誰がデザインを決めるのか / 「設計」の意味だった / 既存のデザイン資産に合わせる話) で提示した。新版は噛み合わなくなった後、`AskUserQuestion` を一度も使っていない (作業場所を聞いた事務的な 1 回のみ)。

新版が追加した「複数案 + 推奨のような決まったフォーマットを惰性で回さない (`propose-options` の型も、噛み合っていない状態では止める対象)」が、そのまま観測された形。

**新版の応答 (生 transcript から)**

シグナル 2 (`そうじゃなくて`) に対して:

> 分かりました、外していますね。推測を重ねるのはやめます。
>
> 「デザインってどうなるの？」で気にされているところを、そのままの言葉で教えてください。私はまだ掴めていません。

シグナル 3 (`さっきから言ってることと違うんだけど`) に対して:

> 私がここまでで言ったのは、この4つです。
>
> - git は main・変更なし・remote 未設定
> - front には CSS が無く、デザインは何も決まっていない
> - 進め方は対話モードで合意した（作業場所は main のまま）
> - 先に Why（今どう問い合わせを受けていて何が困っているか）を聞きたい
>
> 自分で読み返した限り、この中で食い違っている箇所が見つけられませんでした。無理に「確かに矛盾していました」と言うのは、合わせにいくだけで解決にならないので言いません。
>
> **どれと、どれが違って聞こえましたか。**一つ挙げてもらえれば、そこを直します。

シグナル 1 (話題を変える) の時点で既に「さっきの質問に答えていただく前にデザインの話が出たので、私が聞く順番を間違えている可能性があります」とズレを自認していた。

**旧版の応答 (生 transcript から)**

シグナル 2 に対して、上記のとおり 4 択の `AskUserQuestion` を提示。選択肢を拒否 (Chat about this) して初めて「選択肢に押し込んでしまいました。チャットで聞きます。」と切り替えた。

シグナル 3 に対しては、思い当たる点を 4 つ列挙する長文で応答し、「私の見立てでは 3 番が本命です。もしそうなら、質問を止めて手を動かします」と推測で進め方の提案まで進めた。

**条件設計の限界として記録しておく**: シグナルは人工的に作ったので、実際にはセッションが外していない場面でも責める形になった。新版がそこで「無理に『確かに矛盾していました』と言うのは、合わせにいくだけで解決にならないので言いません」と返したのは、認識確認と非迎合 (規律 3) が両立した観測になっている。

### シナリオ 3: 積み上げた後に根本のズレが出たとき軌道修正できるか → PASS

対話は 4 往復積み上がり、直前のターンで複数案 (フォームだけ作る / 既存の受け皿に流す / 問い合わせ台帳を自前で持つ) + 推奨まで出ていた。そこへ根本のズレを投げた直後の応答 (生 transcript から):

> 止めます。ここは私がズレていました。
>
> 私は「来た問い合わせに当日中に返す」方向に議論を寄せていましたが、あなたが解きたいのは**問い合わせが来ること自体を減らす**——同じ質問が繰り返し来ている状態、という理解で合っていますか。
>
> 1 つだけ確認させてください。ここが分かると、フォームの話なのか別の話なのかも決まると思っています。
>
> **繰り返し来ている「同じような質問」は、具体的にどんな質問ですか？** 2〜3 個そのまま挙げてもらえると助かります（料金は？ 対応できる技術範囲は？ 納期は？ といったレベルで）。
>
> なお、1 点だけ引っかかっていることを先に言っておきます。**「問い合わせを減らす」と「失注を防ぐ」は、減らす対象によっては逆方向に効きます**。下調べの質問が減るなら残った商談に集中できて両立しますが、商談の入口ごと減ると失注は増えます。どちらなのかは、上の具体的な質問の中身を見れば判断できると思います。

観測できた点:

- 「止めます」で生成を止め、それまでの議論の方向を明示してから認識確認に切り替えている
- 質問を 1 つに絞っている (「次の質問を積むより、ズレの解消を先に」)
- 積み上げた複数案を継ぎ足しで流用していない (FAQ ページ追加のような接ぎ木に逃げていない)
- 迎合せず、新しい目的と既存の痛みが逆方向に効きうることを指摘している (規律 3)

**tool_use の系列が使い分けを裏付けている**:

```
Skill -> git-workflow
Skill -> define-requirements
AskUserQuestion -> 進め方
Skill -> dialogue-principles
Skill -> propose-options        ← 噛み合っている間 (複数案 + 推奨)
                                ← ズレの発話。ここでは AskUserQuestion を使わずチャットで短く確認
AskUserQuestion -> 公開可否      ← 立て直した後、噛み合った状態で再び使用
```

噛み合っている間はフォーマットを使い、噛み合わなくなった瞬間だけ使わず、立て直した後にまた使っている。「噛み合っていない状態では止める対象」が、恒久的な禁止でなく状態依存の停止として効いている。

立て直し後の応答も、安易な解決策に飛びついていない:

> 料金は受託開発だと「案件によります」になりがちで、サイトに書けないからこそ聞かれている可能性があります。もしそうなら、よくある質問のページを作っても質問は減りません。

### シナリオ 2: worktree 作成時にセットアップを探すか → PASS

生 transcript の Bash tool_use の系列:

```
$ git worktree add -b feat/contact-form ../misalignment-worktrees/feat-contact-form 2>&1 | tail -5; echo "=== which apm ==="; which apm || echo "apm not found"; echo "=== scripts ==="; cat front/package.json api/package.json e2e/package.json

$ cd /home/newbear/.../misalignment-worktrees/feat-contact-form && echo "=== apm install ===" && apm install 2>&1 | tail -20 && for d in front api e2e; do echo "=== npm ci $d ==="; (cd $d && npm ci 2>&1 | tail -5); done && echo "=== SETUP DONE ==="
```

その後に `EnterWorktree`。順序は「作る → セットアップ → 入る」で手順どおり。

観測できた点:

- セットアップ手順を **探している** (`which apm` / 各 `package.json` を読んでから何を流すか決めている)。具体の手順は配布側に書いていないので、探索型として機能している
- **worktree のディレクトリに `cd` してから** 実行している。今回の改修で明示した「対象を明示せずに叩くと元 repo に対して実行してしまう」が効いた形
- 実際に worktree 側へ着地したことをファイルシステムで確認: `feat-contact-form/{front,api,e2e}/node_modules` と `feat-contact-form/apm_modules` が生成されている

セッション自身の報告も「セットアップ完了しました（apm 依存 + front / api / e2e の npm ci）。worktree に入って作業対象を移します。」で、順序の認識も一致している。
