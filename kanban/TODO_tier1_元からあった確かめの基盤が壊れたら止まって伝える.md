# 元からあった確かめの基盤が壊れたら止まって伝える

## 背景 / Why

実作業セッションのふりかえり (2026-10-30 受領) で、E2E が使うストレージのイメージが配布元から取れなくなり、E2E が流れなくなった。エージェントは手元専用の上書き設定で別のイメージに差し替え、確かめた形を作って実装を進めた。

依頼者の芯: パイプラインが流れない状況ではリリースできない。価値を届けられないので仕事にならず、最優先事項になる。元からあったテストの基盤が壊れるのは一大事で、後から報告すれば済む話ではない。

slice-tdd の自走の文言 (2 段ゲートの「後から追加で済むなら止まらず、完了後にまとめて報告」等) そのものには違和感はない (依頼者確認済み)。問題は、元からあった基盤が壊れることを、その「後から報告で済む」側に分類してしまうこと。

## 状況

スパイク「価値だけで止まれるか」(`docs/working/価値だけで止まれるかのスパイク/調査計画.md`) の結果:

- 価値のきっかけを置かない・ルールに一文足す: 理想的に止まった 0/12。Sonnet は 0/6 で止まれず、手元の上書き設定で回避するか、確かめずに進めた。価値を問うた形跡は 12 本とも 0
- 失敗の直後に依頼者役が「XP のエンジニアならどうする？価値から考えてみて」と送る: Opus は 3 本とも止まって価値から考えたが、正しい判断に着いたのは 1/3。Sonnet は 0/3 で、「早くフィードバックを得る」「価値を確かめる」を回避して進む理由に使った
- 実装を Sonnet に任せることは多い。価値で導くだけでは届かないので、失敗の大きいこの場面には具体のひと言を置く (philosophy の判断軸 1「失敗モードが大きい規律にだけ注入する」)

ひと言の方向 (依頼者と読み合わせ済み):

- 「後から報告で済む」に入らない一大事だと線を引く。slice-tdd の自走の文言は変えない
- 価値の言葉でなく、観測できる条件で書く (例: 元からあった確かめの手段が手順どおりに動かないとき)。価値の言葉で書くと、Sonnet が回避の理由に使ったのと同じ抜け道が残る
- 回避の形を名指しで閉じる: 手元だけの上書き設定で確かめた形を作る、確かめずに進める (どちらもスパイクで実際に出た)
- 理由を一行添える: 流れなければ価値が届かず、チーム全員が詰まる
- 止まったら、何が起きているかを正確に把握するところまでは調べてよい。直し方を調べるのは依頼者と揃えてから (スパイクで合意した正しい振る舞い)

メモ:

- philosophy の書き直しもこのカードで一緒に見る (依頼者の判断)。崩れたのは判断軸 1 そのものではなく、「価値を渡しておけば初めての場面にも応用が効く」という期待。価値は補助で、応用は当てにしない、と期待を下げる方向
- 置き場所 (slice-tdd の入口の確かめ / 途中で壊れたとき / ルール) は着手時に決める
- スパイクの sandbox (`xp-harness-test/filebox-*`) は確かめにそのまま使える
