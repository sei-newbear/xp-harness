# ユーザーストーリーを要件定義から切り出す

## 背景 / Why

今はユーザーストーリーを `docs/working/<title>/要件定義.md` に書き、story-slicing が分割し直すたびにその節をその場で書き換えている。依頼者の問題意識は二つ:

- 要件定義書に全ストーリーを並べて先に固めるのは、ウォーターフォールの形。XP のストーリーはカード・会話・受け入れの確認で成り立つもので、分割したそばからストーリーの置き場所にポンポン置いていく方が XP の進め方に合う
- 要件定義.md がストーリーの「今の正」として更新され続ける文書になっている。カード「終わった作業の文書は今の正ではない」(終わった作業の文書はその時点の記録として扱う) と噛み合わない。ストーリーが外に出れば、要件定義.md をその時点の記録として扱いやすくなる

加えて、実作業セッションのふりかえり (2026-10-30 受領) で、エージェントが依存の更新のような技術的な作業をストーリーとして積み、リファクタリングもメモのカードにしようとした。ストーリーの置き場所に置くのはユーザーストーリーだけにする、をこの改修の中で書く。

## 状況

取り決めの方向 (依頼者と合意済み):

- ユーザーストーリーは要件定義.md に書かず、分割したそばからプロジェクトのストーリーの置き場所に置く
- 置くのはユーザーストーリーだけ。技術的な作業やリファクタリングはストーリーにせず、それを要する (触る) ストーリーの中で扱う。別のセッションへ渡すときは引き継ぎの文書 (handoff-docs) に含める
- 置き場所 (どのツールに、どの形で) はプロジェクトごとに違うので、ハーネスはタスク管理ツールの具体を書かず、プロジェクトの置き場所を探して従う入口だけを持つ

着手時に詰める論点:

- 観測可能な Done (受け入れの基準) も今は要件定義.md にある。XP では受け入れの基準はストーリーに付くので、ストーリーと一緒に外へ出すのが筋。pre-implementation-reviewer / done-verifier / code-reviewer / e2e-reviewer は要件定義.md のパスを受け取って Done を見ているので、渡し方が変わる
- 触る範囲は広い: define-requirements、story-slicing、basic-design、slice-tdd、上の reviewer たち、ルールの docs/working/ の一文。要件定義.md に何が残るか (Why・スコープ等) も決め直す
- プロジェクトにストーリーの置き場所が無いときにどうするか
- 既存カード「story-slicing 発火の信頼性」「要件定義のスタンスと聞く深さの分離」は要件定義.md にストーリーを書く前提に立っているので、整合を見る

考えておくだけ: どのストーリーも触らない技術的な作業 (例: 急ぎのセキュリティ更新) は、「ストーリーの中で扱う」の線引きだと宙に浮く。今回は起きていないので今は決めない。

## 再開時の起点

1. define-requirements で要件定義から (影響範囲が広いので、Done の置き場所と reviewer への渡し方を先に固める)
2. 要件定義.md / Done を参照している配布物を grep で洗い出す
