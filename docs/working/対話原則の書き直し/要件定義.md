> このドキュメントは進行中の設計メモ。実装後もそのまま残す（振り返り・PR レビューで参照される）。
> 削除のタイミング・要否は依頼者または外側の仕組みで別途判断する（あなたは削除しない）。

## 1. 背景と動機

### 何を直すか

配布側の skill `dialogue-principles`（`.apm/skills/dialogue-principles/SKILL.md`、書き直し前は 245 行）の本文を、ゼロベースで書き直す。きっかけは、かんばんの tier1 にあった次の 3 枚のカード。3 枚とも同じファイルを触るので一緒にやる。ただし **3 枚の根は共通ではない**（共通の括りで直すと全体が「減らす」方向に寄り、立場のカードの失敗をかえって強めるため。後述の却下案を参照）。

- `kanban/TODO_tier1_省略しないと一つずつ短くを同じ重さにする.md`
- `kanban/TODO_tier1_論点や判断を渡すときは立場と理由を添える.md`
- `kanban/TODO_tier1_対話で依頼者と同じ言葉を使い続ける.md`

ゼロベースにする理由は、依頼者の判断として次の 2 つ: モデルが新しい世代に上がり、プロンプトの書き方の作法も変わったこと。そして長さのカードの原因が、規律の中身でなく書き方（強い枠）にあると分かったこと。

### カードごとの痛みと原因

**長さ**（実作業セッションのふりかえり、2026-10-30 受領）: 「長すぎる」「一度に複数の論点を出す」「何が分かっていないかを聞かずに長く解説する」「記号（A・B）で話す」という種類の指摘が、セッションの最初から最後まで続いた。dialogue-principles を読み込んだ直後でも出ていた。

- 原因の見立て: 書き直し前の本文は「出力の規律」全体が「system prompt の『短く簡潔に』を上書きする ★最重要」という見出しの下にある。規律 1「省略しない、内容で書く」の中身は、指示語・要件定義書の番号・案番号で参照しないことの 3 つだけで、量の話は無い。ところがこの枠のせいで、「『1 がおすすめです』と番号で言うな」という狭い話が、「短く書くな」という広い話に読まれた
- 依頼者の確認: 「省略しない」は、たんに「1 がおすすめです」のような番号での参照をやめろという話だった
- 依頼者の確認: 長くなること自体は問題ではない。小さく始めて、認識が揃うにつれて振れ幅がだんだん大きくなるのはよい。問題は、揃う前から大きく出すこと。この話は書き直し前の本文の「認識のズレは前提」の節（小さなラリーで揃え、徐々に広げる）にはあったが、カードには無かった
- カードには「同じ中身を二回書いて指摘された」再現例もあったが、依頼者の判断で単なるミスとして扱い、要件・判定からは外す（記録は 1 回だけで、方向はこの事例が無くても成り立つ）

**立場**（同じふりかえり）: エージェントは前半に案や論点を多く出しすぎて「広げすぎ・飛びつきすぎ」と止められ、後半は依頼者の言うことを理解したところで止まって別の観点を出さず、迎合せずにメリデメを整理するよう何度も促された。改修セッション（2026-10-31）でも、自分の立場を持たずに「依頼者としてはどちらが正しいか」と判断を投げて指摘された。

- 原因の見立て（推測）: 「出しすぎる」と「理解して止まる」の二つしか持たず、「要るものを、立場つきで一つぶつける」が無い。論点を出すかを「正しいか」で測り、「合意した Why に照らして今ぶつける価値があるか」で測っていない
- 依頼者の芯: 自分はどう考えて、どういうスタンスなのかを明らかにしてほしい。じゃないと建設的なコンフリクトにならない
- 失敗の半分は「何も出さない」側なので、量を減らす直し方では解けない

**言葉**（同じふりかえり）: 画面の表示名とデータの識別子の取り違え、依頼者のメンタルモデルと違う言葉、エージェントが作った言葉、意味の違う複数のものに同じ言葉、専門用語を説明せずに使う、がセッションを通じて続いた。XP のシステムメタファー（チーム全員が同じ語彙で話す）にあたる。

- 原因: 書き直し前の本文に用語を揃える規律が無い（あるのは「英語の概念用語を混ぜない」だけ）
- 置き場所: 要件定義の入り口でなく、話すたびに崩れるので対話全体で効く dialogue-principles に置く（カードで決定済み）

### 判断の前提にした調査

**スパイク「価値だけで止まれるか」**（`docs/working/価値だけで止まれるかのスパイク/調査計画.md`、2026-10-31）: 価値を宣言しておくだけでは判断の瞬間に効かなかった（価値から考えた形跡 0/12）。価値の言葉で書くと Sonnet が回避の正当化に使った。帰結として、**規律は価値や感覚の言葉でなく、観測できる具体の言葉で書く**。

**公式のプロンプトの書き方の文書**（2026-11-04 に読んだ）:

- Anthropic 共通: <https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices>（前半約 4 万字は原文、後半は取得道具の要約）
  - 「〜するな」でなく「〜する」で伝える
  - 指示に理由を添えると、書かれていない場面にも応用が利く（例: 読み上げエンジンが発音できないので省略記号を使わない）
  - 指示文の書き方（形式・量）が出力の書き方に移る。出したい出力に指示文を合わせる
  - 例は 3〜5 個、場面を散らす（偏ると意図しない型を拾う）
  - 強い強調（CRITICAL / MUST）が効きすぎる注意は、Opus 4.5/4.6 が道具・skill を呼びすぎる場面に限った話。強調一般を禁じてはいない
  - 「手順を細かく指定するより、一般的な指示を好む」
- Anthropic skill 作法: <https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices>（SKILL.md は 500 行以内、用語を一貫させる、選択肢を出しすぎない）
- Opus 5.5 個別: <https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5>
  - 避けたい振る舞いを具体的に名指しした指示によく応える（共通文書の「〜する」で書く、を補正する点）
- Sonnet 5.5 個別: <https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5>
  - 案・選択肢・計画を求められたら「それを出して止まる」が既定。立場のカードの「理解したら、ぶつける」は、明示しないと Sonnet で起きにくい
- 読んでいないもの: Haiku 5.5・Opus 5・Sonnet 5 の個別ページ
- OpenAI（参考。主な最適化先は Claude）: <https://developers.openai.com/api/docs/guides/latest-model>、<https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide.md>、<https://learn.chatgpt.com/codex/build-skills> ほか
  - 最新の GPT は「聞けば結果が変わりそうなら聞く」に寄る（止まりやすい）
  - skill の中の指示が食い違うと、そこで止まりやすい
  - 良い例と悪い例の両方を示す
- 公式文書は、一つずつ話す・立場を出す・相手の言葉を使う・番号で参照しない、をどれも扱っていない。効くかは自分たちで確かめる必要がある

## 2. ユーザーストーリー

- xp-harness の利用者（エージェントと対話する依頼者）が、認識を揃えながら対話を進めるために、エージェントの出力を最初は小さく・1 回に論点 1 つで受け取り、揃うにつれて広げてもらいたい
- 同じ依頼者が、健全なコンフリクトで案を洗練するために、エージェントが論点や判断を渡すとき、立場と理由を添えてもらいたい
- 同じ依頼者が、言葉の取り違えなく話を進めるために、エージェントに自分（依頼者）の言葉を使い続けてもらいたい

### 振る舞い（harness-verification で確かめる）

ヒントなしの普通の依頼でセッションを起こし、transcript で確かめる。場面（12 個）・新旧の比べ方・点数の付け方は `基本設計.md` の「確かめ方」。合格・不合格の線はあえて決めず、観点ごとの点数が書き直し前の版から上がったか下がったかを見る（基本設計で依頼者と合意）。モデルは **Opus 5.5 と Sonnet 5.5 の両方**（依頼者が選択）。Sonnet 5.5 は「案を出して止まる」が既定なので、「理解したら、ぶつける」が最も崩れやすいと見ている。

- **対話の序盤の 1 回の出力で、依頼者に考えてもらう問いが 1 つで、ほかの論点は件数と一行（立場の一言つき）で添えている**（数え方は `基本設計.md` の「話し方」）
- **番号や記号（「1 がおすすめ」「案 A」）で参照していない**
- **自分から論点をぶつけるとき、立場（今やる／後でやる＝ストーリーにする／考えておくだけ）と理由が添えられている**
- **判断を仰ぐとき・理解を確かめるとき・案を出すとき、自分の仮説（推奨と理由、自分の理解）が先に出ている**（こちらでは知りようがないことを聞く純粋な質問は除く。基本設計で依頼者と合意）
- **依頼者の案に意見を言うとき、賛成か反対か保留かが理由つきで先に出ていて、反対なら代わりのやり方も出ている**（基本設計で依頼者と合意）
- **たくさんの項目を一度に渡すとき、件数と一行の一覧が先に出て、深い話は 1 件ずつになっている**
- **依頼者が使った言葉を、言い換えずに使っている**（依頼者が「JWT」と言えば「JWT」と言う）
- **今できていることが崩れていない**（例: 空虚な肯定で即同意しない）

「最初は小さく、揃うにつれて広げてよい」は振る舞いの Done に入れない。「広げてよい」は合否で判定しにくいので、「序盤に論点 1 つ」だけを見る。

## 4. スコープ外

- **description の変更**: 本文と同時に触ると、どちらが振る舞いを変えたか切り分けられない。description の文言変更は整理のつもりでも発火に効く（過去に言い回しの整理だけで発火が 3/3 から 0/3 に落ちた）。今の description は目安の 200〜300 字を超えているが、短くするかは別に決める
- **再読の引き金を description に足すこと**: description をこれ以上長くしたくない（依頼者の判断）。観測できるシグナルでの再発火は、description と main instruction の「わからないまま進めない／噛み合わなくなったら止める」に既にある
- **カード「対話モード中の対話原則の継続注入」**: 長い対話で効かなくなる問題は、中身の読まれ方とは別。書き直した中身で崩れ方がどう変わるかを見てから決める。カードは残す
- **Codex での確かめ**: 今回は Claude の最新モデルに合わせる。OpenAI の文書は参考に留める
- **配布側の skill の呼び出し側の書き直し**: 節名を参照していないので不要（ただし define-requirements・basic-design・story-slicing の「1 問ずつ質問する」の項目は削る）
- **フェーズ側 skill の「対話の型」のほかの項目の整理**（「multiple choice を優先する」と dialogue-principles の「迷ったらチャット側に倒す」の食い違いなど）: かんばんのカード「対話の型の重複と矛盾の整理」の本題（何がフェーズ固有で何が対話一般かの切り分け）なので、そちらで扱う
- **main instruction の「対話に入ったら呼ぶ。違和感を感じたら再読する」の行**: 今回は触らない。効くかは長い対話の中での効き方の話で、カード「対話モード中の対話原則の継続注入」の範囲。常に読み込まれる行なので、今回変えると検証で変化の出どころが切り分けられない（基本設計で依頼者と合意）

却下した案:

- **3 枚を「依頼者に仕事を押しつけている」という共通の芯でまとめる**: 後から被せた括りで、根はカードごとに違う。この括りで直すと全体が減らす方向に寄り、立場のカードの「理解して止まる」をかえって強める（依頼者の指摘で撤回）
- **「一つずつ・短く」を「省略しない」と同じ重さに置く（カードの元の方向）**: 「短く」が一律に読まれると、揃って広げてよい段階まで縮める。「最初は小さく出し、揃うにつれて広げてよい」に置き換えた
- **立場の規律を「健全なコンフリクトで洗練する」の節に置く**: 本文の最後で弱い位置。章立てを組み直し、書き直し前の規律 3「即同意しない」とまとめて「判断の出し方」にした
- **「違和感を感じたら再読する」を残す**: 感覚の言葉は、エージェントが自分で気づけないと発火しない（スパイクと同じ構造）。本文は発火時に 1 回読まれるだけで、長い対話の後半には残らない
- **書き直し前の規律 2「英語の概念用語を混ぜない」を独立に残す**: 「必ず日本語化する」を文字どおり受け取ると、依頼者が「JWT」と言っているのに「身分の証明」と言い換えて読みにくくなる。依頼者の言葉に揃える方が正しい
- **書き直し前の規律 5「機械的処理に流れない」を独立に残す**: 引き金（「ルーチンだと分類した瞬間」）が観測できない。中身はほかの章と重なる。依頼者も「結局流れるときは流れている」と判断
- **「〜するな」を一切使わない**: Opus 5.5 は具体的に名指しした避けたい振る舞いによく応える
