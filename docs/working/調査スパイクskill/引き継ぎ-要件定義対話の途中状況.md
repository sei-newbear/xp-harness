## 最重要の決定: skill の位置づけ (要件定義.md を上書きする)

依頼者との対話で確定した、書き起こし後の最大の転換:

**この skill は横断的な補助 skill ではなく、slice-tdd と同格の「実行フェーズ skill」。作業クラスが「調査」のときの実行 skill である。**

- 要件定義 → define-requirements、実装 → slice-tdd と同じ並びで、調査 → 本 skill
- slice-tdd が「どう TDD で回してどう成果を届けるか」を持つのと同型で、「どう調査を回してどう知見を届けるか」を持つ。やることが実装か調査かの違いだけでレイヤーは同じ
- **呼ばれ方はフェーズ routing と同じ場所**: 依頼冒頭のフェーズ判定と、main.instructions の「フェーズと skill」の並びに「調査 → 本 skill」として載る
- **slice-tdd 本文から呼ぶ案は依頼者が明確に否定** (却下理由: 実装フェーズに入っている時点で作業クラス判定は済んでいるので構造として遅い。slice-tdd は自走モードの skill であり、そこから調査 skill に入るのは導線として合わない)
- 埋め込みスパイク (ストーリー進行中の切り出し) は「実装中のサブルーチン呼び出し」ではなく、**作業クラスが実装から調査に切り替わるフェーズ遷移** (実装 → 調査 → 実装に戻る) として扱う
- TDD との違い (依頼者の言): 調査のサイクルは TDD より速いだろうし、調査の後に依頼者の判断を求めることがある

この転換の経緯: 当初 main session が「slice-tdd 本文に呼ぶ案内を追記 + main.instructions に横断 skill (propose-options 同格) として登録」を提案 → 依頼者が「違う」「足りない」と否定 → 「TDD skill と同じレイヤー」という依頼者の位置づけで確定した。

## 理想の調査の認識合わせ (対話で合意済みの部分)

依頼者と「理想の調査」をフェーズ分割 (入口 / 最中 / 出口) で認識合わせ中。ゴールから逆算する方針で、出口 → 最中 → 入口の順に話している。

### 出口 (合意済み)

出口は 2 ケースある: (1) エージェントがそのまま知見を使って進むケース、(2) 依頼者に報告して判断を仰ぐケース。

**決定: エージェント自走消費のケース (1) は今回スコープ外。skill の出口は「依頼者への報告 / 次工程への引き継ぎ」に絞る。**

根拠 (依頼者合意済み):
- 実痛み 3 件 (AgentTeam スパイクの引き継ぎ欠落 / apm 調査の報告読みにくさ / compile 反証漏れ) の出口は全部「知見が依頼者の判断・次工程に渡る」側で、自走消費側で顕在化した痛みは記録に無い
- 自走中の小さい調べ物は既に「その場で消費される調べ物は発火しない」で除外済み
- それより大きい自走中の迷いは slice-tdd の止まる/進む判断軸が既に統べている
- 痛み未顕在に装置を作るのは philosophy の象限 4 (痛みが見えてから)

**依頼者向け出口の理想 = harness-verification の「検証レポート」書式の調査版** (依頼者が「検証スキルを見てくれ、それが近い」と指定し、以下で合意):
- 実況と報告を地続きにしない: はっきりした区切りを立てて「ここから報告」
- 最抽象の結論から: 問いへの答え + 平易な意味 + 確信の温度感 (どこまで調べ切ったかの厚み、残リスク含む)
- 抽象度を上から下へ: 結論 → 詳細 (何をどう調べたか) → 証拠 (生データで裏を取ったものだけ)
- 提案は軽く、確定しない: 次の一手は出すが判断は依頼者に残す。propose-options 型に乗せるのは判断が実際に分岐するときだけ

書式の出典は `.claude/skills/harness-verification/SKILL.md` の「報告は『検証レポート』の書式で出す」section。重複照合 (後述) の第一候補になる。

### 最中 (合意済み)

理想 4 項目:
- **反証で開く**: 裏付け一発で閉じず、判断が壊れる道を潰しにいく
- **現実の初期状態で試す**: きれいな環境でなく、利用者の現実 (既存資産あり等) を再現する
- **小さく速く回す**: 小さい実験の繰り返し。作り込まない、捨てる前提
- **事実と推測を分けて積む**: 観測と解釈をラベルで区別、集計や自己報告を鵜呑みにしない

調べ方の種類は 2 分類 (依頼者と合意):
- **情報取得型**: 読む・探す。一次情報で裏を取る
- **仮説検証型**: 仮説を明示して試す。実験・観測はこのループの中の動作 (「実験型」を独立の型とせず仮説検証型に内包させた。単発の「動かして見てみる」も暗黙の仮説を持つ。仮説の明示に規律価値がある — compile 調査の実痛みは「問題ないだろう」という暗黙の仮説を明示しなかったから反証にいけなかった)

注意: 「壊れる道の列挙に戻る」「列挙が全部潰れたら完了」のような入口の形を先取りする項目は、依頼者の指摘で最中の合意から外した (入口が未議論のため)。

### 入口 (未着手・次の議論)

- 依頼者の認識: 「入口はいろいろある」(ぬるっと入る / 計画を出してから / 最初から調査依頼、事前準備の度合いも変わる)。**最後に話すと依頼者が明言**
- 発散で出した軸 (未収束): 入り方 / 事前準備の重さ / サイクルの形 / 出口 (→合意済) / 宛先 / 関与の深さ

## skill-reviewer 壁打ちから得た未処理の論点

skill-reviewer (改修者向けレビュー subagent) との壁打ちで出た、まだ依頼者と議論していない論点:

- **description は観測サインで書く**: 実痛みは「スパイクと認識できず流し込んだ」= 認識の失敗なので、「XP スパイクとして切り出す作業」という作業クラス名の宣言では名指せた人にしか効かない。「試してみないと分からない」「調べないと次の判断を決められない」のような状況記述に寄せる (フェーズ skill 化した今も、埋め込みスパイクの認識問題としては生きている論点)
- **スパイクの「出口」(使い捨ての担保・元の作業への復帰) が 4 工程 (始め方/調べ方/残し方/仕上げ) に無い**: 埋め込みスパイクで「切り出したまま戻らない」「使い捨てコードが本実装に育つ」失敗が構造的に起きうる。フェーズ遷移 (実装 → 調査 → 実装に戻る) と位置づけた今、「戻る」の設計はより重要になった
- **スパイク中の slice-tdd 規律との共存**: 実装中に切り出すと slice-tdd 発火済みのまま。使い捨て前提のスパイクに TDD 規律 (テスト先書き・code-reviewer・done-verifier) をそのまま適用すると噛み合わない。「スパイク中は実装サイクルの規律の外に出る、出た範囲はここまで」を本文が宣言する必要 → 基本設計の論点

## 決定済み事項の要約 (要件定義.md に反映済みのもの)

- 責務境界: 配布側 `.apm/skills/` (スパイクは XP 由来の進め方の規律)
- 発火の輪郭の錨: XP のスパイクのノリ (問いに答えるための使い捨て前提の小さな実験・調査。成果物は知見)。カード化された独立スパイクも、進行中に切り出す埋め込みスパイクも対象。その場で消費される調べ物は対象外
- skill の核: 「問いに答える」でなく「判断の危険を潰す」
- 報告書式・反証可能性の harness-verification との集約方式: **重複許容で開始** (依頼者判断)。新 skill を書いた後に突き合わせ、同内容ならその時点で切り出す
- instruction の仮置き芯 (「新しいライブラリ・ツールは思想を調べてから使う」) の移設: **スコープ外** (skill 発火前に効くべき規律のため。依頼者指摘で一度の合意を覆した)
- スコープ外: retrospective 裏取り拡張 (別カード) / harness-verification の検証固有規律 / handoff-docs・handoff-verifier 本体 / 発火率検証 (事後評価)
