# 調査スパイク skill — 本文を書いた後の照合記録

> 本文（`.apm/skills/research-spike/SKILL.md`）を書いた後に下した 2 つの判断の記録。
> 要件定義の完了基準のうち「困りごとと本文の対応が書き出されている」「harness-verification との重複照合の判断が記録されている」に対応する。

## 1. 困りごとと本文の対応

要件定義の背景に挙げた困りごとそれぞれについて、本文のどこが効くかを書き出す。

### 引き継ぎが落ちた（完了を早く宣言し、引き継ぎ点検は促されて実施した）

効く場所:

- 「どこで終わるか」— 完了を「問いに答えた」ではなく「入口で合意した意図に到達したか」で見る。基準が自分の中に無いので、答えが出た時点で完了を押せない
- 「報告のあと」— 報告を出した後に、書き起こすかどうかと誰向けかを依頼者に確認し、作ると決まったら引き継ぎ文書を書く skill を呼ぶ動線がある

**残る穴**: 引き継ぎ文書を書いた後の文脈ゼロ点検は、呼ぶ skill（`handoff-docs`）の側が持っている。本 skill は呼ぶだけなので、点検の実行はそちらに依存する。これは意図した責務分担。

### 報告が実況の地続きになった（結論が冒頭に区切られず、要点に届かない）

効く場所:

- 「報告する」— この章だけ具体的な書式を持つ。はっきりした区切りを立てて「ここから報告」、結論 → 詳細 → 証拠、確信の度合いを結論に含める、提案は軽く出して判断は依頼者に残す

本文全体の方針は「手順を持たず判断の拠り所だけ持つ」だが、ここだけ例外にしてある。理由は、この失敗が実際に 2 回起きていること、および公式の指針が「応答は長くなりがち・実況しがちなので、長さと伝え方は明示的に指示せよ」と言っていること。

### 壊れる方を確かめずに閉じた（一つの角度を裏付けて閉じ、判断が外れる条件を見に行かない）

効く場所:

- 「調査の計画を立てて合意する」— 何が確かめられていればその判断をしてよいかを、調べる前に計画として出す。計画をファイルに出すのは、確かめどころを自分一人の想像力で決めさせないため（現場の実態は依頼者側が持っていることがある）
- 「調べる」の反証で開く — 裏付けを一つ取って閉じず、判断が外れる条件の方を確かめにいく
- 「調べる」のミニマムから小さく速く回す — 現実の条件は、反証で当たりにいく対象の一つとして後から寄せる
- 「調べたことを計画に反映する」— 計画に書いた「これが確かめられていれば判断してよい」の横に分かったことが並ぶので、埋まっていない確かめどころが見て分かる

**承知の上で残す未カバー**: 名指しで呼ばれなければ、これらは一切効かない。この困りごとが起きた場面（作業の途中で生えた調べ物）で誰も skill を呼ばなければ素通りする。発火の設計は 2 本目のユーザーストーリーに分離してある。

## 2. harness-verification との重複照合

### 照合した対象

改修者向けの `harness-verification` skill が持つ「報告書式」と「反証可能性」の規律を、新しく書いた `research-spike` の本文と突き合わせた。

### 報告書式 — 重なるのは 4 点、それ以外は別物

重なる部分:

- 実況と報告を地続きにせず、はっきりした区切りを立てる
- 抽象度を上から下へ（結論 → 詳細 → 証拠）
- 結論に確信の温度感（どこまで調べ切ったかの厚み）を含める
- 提案は軽く出し、判断は依頼者に残す

重ならない部分（`harness-verification` 固有）:

- 全体結論が PASS / FAIL の形を取る
- シナリオ一覧という中間の層がある（複数シナリオを入れ子にする）
- 詳細に「再現粒度」（sandbox の種別・仕込んだ状態・依頼文の全文・前後比較の有無・試行数）を要求する
- リリース可否の目線で温度感を出す
- 自走実装セッションの分析では、サイクル構造と時間配分の 2 セクションを追加する
- 検証記録を所定の場所に永続化する動線を持つ

重ならない部分（`research-spike` 固有）:

- 判定の形を持たない（調査は合否を出す作業ではない）
- 次の一手を出す先が、検証の可否ではなく次の判断・工程

### 反証可能性 — 名前が同じで中身が違う

- `harness-verification` の反証可能性は、**検証条件の弁別力**の話。仕込んだ条件が、対象の核が欠けていたときに FAIL を出せる設計になっているかを問う
- `research-spike` の「反証で開く」は、**調べ方**の話。裏付けを一つ取ったところで閉じず、判断が外れる条件を確かめにいく

共有しているのは「一つの肯定で満足しない」という発想だけで、規律としての中身は別物。

### 判断: 重複を維持する（集約しない）

理由は 2 つ。

**中身が割れた。** 書く前に予想したとおり、報告書式の共通部分は 4 点にとどまり、それぞれが固有の中身をかなり抱えている。反証可能性に至っては、名前が同じで指すものが違う。共通部分を切り出しても、両側から呼んだ先で「ここから先はそれぞれ別」と分岐するだけで、規律を 1 か所にまとめた実益が薄い。

**参照の向きが取れない。** `harness-verification` は改修者向けで配布されない。`research-spike` は配布される。**配布側から非配布側への参照は、展開先に参照先が存在せず壊れる。** 逆向き（`harness-verification` が `research-spike` を呼ぶ）は成立するが、それをやると改修者向けの検証手順が配布物に依存する形になり、検証固有の中身（再現粒度・PASS/FAIL・記録の永続化）を配布側に持ち込むか、呼んだ先で足りない分を上書きするかになる。どちらも今の切れ目に合わない。

**再検討する条件**: 将来どちらかの固有部分が痩せて、共通部分が大半を占めるようになったら、そのとき改めて切り出しを検討する。切り出す場合の置き場所は、配布側に置いて `harness-verification` から呼ぶ向きに限られる。
