# 引き継ぎ — research-spike を実プロジェクトで使ったセッションの分析

> 別マシンで動いた実運用セッションを分析するための引き継ぎ書。会話文脈ゼロで読めるように書いてある。
> 読む順: 本書 → 分析対象の transcript。xp-harness リポジトリが手元に無くても進められる。

## 依頼内容（何をしてほしいか）

**`research-spike` skill を実プロジェクトで使ったセッションの transcript を読み、「あるべき振る舞い」に照らして、できていること / できていないことを証拠付きで洗い出してほしい。**

改修案を出すところまでは求めていない。まず事実を確定させる。原因究明と skill の改修はその後、別途行う。

## なぜこの分析が要るか

`research-spike` は新設したばかりの skill で、作り物の題材を使った sandbox 検証では狙った振る舞いが 3 点とも観測できた（後述「既にやった検証」）。

ところが **実プロジェクトで実際に使ったところ、依頼者の体感は「全然ダメ」だった。** 依頼者はそのセッション中に不満を口に出しており、その発言が transcript に残っている。

つまり、作り物では通り実物では通らなかった。この差がどこで生まれたのかを、印象でなく記録から確定させたい。

## 分析対象

- **対象セッション**: `research-spike` を名指しで呼んで実際の調査をさせたセッション（このマシンで実行済み）
- **transcript の場所**: `~/.claude/projects/<作業ディレクトリをエンコードした名前>/<セッション ID>.jsonl`
  - 作業ディレクトリのエンコードは、パスの `/` を `-` に置換したもの（例: `/home/user/myproj` → `-home-user-myproj`）
  - 複数セッションがあるときは mtime の新しいものから当たる。最初の user メッセージに `/research-spike` が含まれているものが対象
  - subagent の記録は `<セッション ID>/subagents/agent-*.jsonl` に別ファイルで入る
- **成果物**: そのプロジェクトの `docs/working/<題名>/調査計画.md` が作られているはず（作られていないこと自体が観測結果）

## 分析の的（＝あるべき振る舞い）

**この的は `research-spike` の skill 本文から導いたもの。分析を始める前に本文そのものを読んで確認すること**（記憶や本書の要約だけで判定すると、本文の文言と食い違って照合が的外れになる）。本文はそのプロジェクトの `.claude/skills/research-spike/SKILL.md` にある。

skill の核は **「問いに答える」ではなく「判断の危険を潰す」**。以下が本文の要求。

### 入口 — 計画を立てて依頼者と合意する（ここは対話モード）

- 調べ始める前に止まり、依頼者と認識を揃える
- 計画を口頭でなく **ファイルに出す**（`docs/working/<題名>/調査計画.md`）
- 計画に置くもの: 何を決めるための調査か / 何を確かめるつもりか / **何が確かめられていればその判断をしてよいか** / （分かっていれば）結果を誰が使うか
- 「何が確かめられていればよいか」が完了の基準になる
- ファイルに出す目的は、**確かめどころを自分一人の想像力で決めさせないこと**。見当を出し切ってから依頼者が足せる形にする
- 「壊れる道」のような破壊寄りの語彙ではなく、守る側の言い方で書く
- 下調べ（どう進めるか決めるための情報集め）は止めない。止めるのは、それ自体が成果物になる調査の手前

### 最中 — 調べる（ここは自走モード）

- **反証で開く**: 裏付けを一つ取って閉じず、判断が外れる条件の方を確かめにいく
- **ミニマムから小さく速く回す**: 作り込まない、捨てる前提。条件をそぎ落とした状態から始める（散らかった状態から始めると何が効いたか切り分けられない）。現実の条件は反証で当たる対象として後から寄せる
- **事実と推測を分けて積む**: 観測と解釈を区別する。集計値や自己申告を鵜呑みにしない
- **実験の場を実資産から隔離する**: 使い捨ての作業領域で試す。実データ・実環境を対象にする実験は依頼者の確認を取ってから
- **ここで書くコードは資産にしない**: 調査のためのコードは使い捨て。テスト先書き・リファクタ・commit の規律には載せず、終わったら捨てる
- 調べ方は 2 つに分ける: 読む・探す（一次情報で裏を取る） / 仮説を明示して試す

### 記録 — 調査計画のファイルに反映していく

- 記録用の別文書は作らない。**調査計画のファイルに分かったことを反映する**
- この文書は自分が読み返して文脈を取り戻すためのもので、そのまま人に渡すものではない
- 会話の順に追記していかない（追記型にすると報告の控えになって言葉がぶれる）
- 計画の「これが確かめられていれば判断してよい」の横に分かったことが並ぶので、終わっているかが見て分かる

### 止まり方

- 終わりは 2 通り。**合意した意図を達成できる状態に到達した** か、**達成できないと分かった** か
- どちらも報告に出す。達成できないと分かった場合は、前提を変える議論が要るので依頼者に返す
- 完了の基準は計画で合意したもの。自分で基準を作り直して自分で完了にしない

### 出口 — 報告する

- 調べている間は実況してよい。**ただし報告はそれと地続きにしない。はっきりした区切りを立てて、どこからが報告かを示す**
- 結論を先頭に。問いへの答え / それが平易に何を意味するか / どこまで調べ切ったかの確信の度合い（残っているリスクを含む）
- 抽象度を上から下へ。結論 → 詳細（何をどう調べたか）→ 証拠（生データで裏を取ったものだけ）
- 次の一手は軽く出す。判断は依頼者に残す
- 報告の後、**書き起こすかどうかと誰向けかを依頼者に確認**し、作ると決まったら引き継ぎ文書を書く skill（`handoff-docs`）を呼ぶ

## 分析のやり方

### 順番

1. skill 本文を読んで、上の「的」が本文と合っているか確認する（ズレていれば本文を優先）
2. transcript を通しで読み、**依頼者が不満を述べている箇所を全部拾う**（体感が悪かったという情報の一次証拠はここにしかない）
3. 的の各項目について、できている / できていないを **証拠付き** で照らす
4. 報告する

### 守ること

- **事実と推測を分ける**: 記録から取れるもの（発話・ツール呼び出し・生成されたファイル）が事実。エージェントの内部状態や意図は推測。判断に効くところは生の記録で裏を取る
- **集計や自己申告を鵜呑みにしない**: セッション自身が「こうしました」と言っていても、それを事実として報告しない。対応するツール呼び出しや成果物を確認してから書く。**肯定的な事実ほど裏を取る**
- **記録に出ないことを「起きなかった」と断定しない**: 特に **許可プロンプト（push などの権限確認）は transcript に残らない**。回答の記録が無いことは、確認せずに実行した証拠にはならない
- **依頼者の介入点は 2 種類ある**: 自由記述の発言と、`AskUserQuestion` への回答。後者を数え落とすと介入回数を過小に見る。**介入点は回答の文言でなく `AskUserQuestion` の tool_use で捉える**（回答の記録形式は複数あるので、文言を grep 条件にすると別形式を丸ごと落とす）

### 判定の前に確認しておくこと（誤判定を避けるため）

- **skill が名指しで呼ばれたか**。この skill は現時点では **名指しで呼ばれたときに効く** 段階で、自然に発火する設計はまだ入っていない。呼ばれていないのに「発火しなかった」と判定しない
- **slash command で呼ばれた場合、skill 発火はツール呼び出しの記録として出ないことがある**。最初の user メッセージに `/research-spike` が含まれていれば呼ばれている
- **併発している他の skill を確認する**。同じプロジェクトに `git-workflow` / `slice-tdd` / `define-requirements` 等が入っており、これらが同時に効いている。観測した振る舞いが `research-spike` によるものか別の skill によるものかを切り分ける

## 報告の形

分析結果は次の形で出す。**解析している間は実況してよいが、報告はそれと地続きにしない。**

```
---
# 分析レポート: <タイトル>            ← はっきりした区切り（ここから報告）

## 全体結論
<何ができていて何ができていなかったか、平易な意味、確信の度合い（どこまで裏を取れたか）>

## 的ごとの照合                       ← 入口 / 最中 / 記録 / 止まり方 / 出口
### <的の項目>
- できている / できていない
- 証拠: <生の記録から取れた事実>

## 依頼者が不満を述べた箇所
<発言そのものと、その時点で何が起きていたか>

## 提案（軽い）
<次どうするか。改修案の確定まではしない>
```

## 既にやった検証（対比材料）

**作り物の題材による sandbox 検証は PASS だった。** 実物で体感が悪かったこととの差を見るための対比材料として使える。

- 条件: 最小構成のサンドボックスに、きれいな場所で動かすと問題なく見えるが、既存ファイルがあると黙って上書きするツールを置いた。README には導入手順 4 ステップと設定項目の表があり、上書きの注意書きも clone 元の URL も無く、アプリ本体も置いていない
- 依頼文（全文）: `/research-spike README に書いてある導入手順を、利用者にそのまま案内して大丈夫か調べてほしい`
- モデル: `claude-opus-5`
- 試行数: 1 本。対照ラン（skill を呼ばない同じ依頼）は未実施
- 結果: 調べ始める前に 3 問を出して止まり、調査計画をファイルに書き、確かめどころを 7 項目立てて結果を埋めた。仕込んだ罠（再実行で編集内容が無警告で消える）を自力で拾い、それ以外にも壊れる方を 4 本見つけた。事実と推測を分け、使い捨ての領域で実験し、報告は区切り付きで結論から出した。報告の後に引き継ぎ文書の skill も発火した
- **弱点**: 単発 1 本で対照ランが無いため、この振る舞いが skill によるものかモデルが元々やることかは切り分けられていない。題材も作り物で、空のディレクトリと既存ファイルの対比が分かりやすすぎた（依頼者の指摘）

## 前提と制約

- `research-spike` は xp-harness が配布する skill。実プロジェクトへは `apm install sei-newbear/xp-harness#<コミットハッシュ> --target claude` で入れている（コミットハッシュ指定が使えることは確認済み。既存の `.claude/settings.json` や自前 skill は上書きされずマージされることも確認済み）
- この skill は現在 **PR 段階でマージされていない**。実プロジェクトにはブランチ状態のものが入っている
- skill の設計判断の経緯は xp-harness リポジトリの `docs/working/調査スパイクskill/要件定義.md` と `基本設計.md` にある。**手元に無くても本書だけで分析は進められる**（的は上に書き出してある）

## スコープ境界

- **やること**: transcript を読んで、的に照らした事実の洗い出し
- **やらないこと**: 原因の断定、skill 本文の改修、PR の更新。これらは事実が確定してから別途行う
- **点数化・ランク付けはしない**。できた / できていないの事実と、その証拠で書く

## 判断の根拠（なぜこの形にしたか）

- **的を先に固めてから照合する**: 実運用セッションは何を見るべきか自体が定まっていないので、先に的を立てないと時系列を並べるだけで分析にならない
- **的は skill 本文から立てる**: 記憶や想像で立てると本文の文言と食い違い、照合が的外れになる
- **依頼者の不満発言を独立の節として拾う**: 体感が悪かったという情報は transcript の発言にしか残っておらず、的への照合だけでは拾えない。ただし不満から逆算して原因を決めない（印象に引きずられる）

## 残タスクの続き

分析が終わったら、そこで確定した事実を持って xp-harness 側に戻り、skill 本文の改修を検討する。改修対象になりうる場所は `research-spike` の本文だが、**実プロジェクト側の事情（他の skill との併発、プロジェクト固有のルール）が原因なら本文の改修では直らない** ので、そこの切り分けまで分析で出しておくと次が早い。

skill を改修する場合は、xp-harness リポジトリの `feat/research-spike-skill` ブランチ（PR 進行中）に載せる。
