# 調査スパイク skill 新設 — 基本設計

> このドキュメントは進行中の設計メモ。実装後もそのまま残す（振り返り・PR レビューで参照される）。
> 削除のタイミング・要否は依頼者または外側の仕組みで別途判断する（あなたは削除しない）。
>
> 前提となる要件は同じディレクトリの `要件定義.md`。本書はその要件を満たす「どう作るか」を決めたもの。

## 0. この設計が対象にする範囲

要件定義でユーザーストーリーを 2 本に分けており、**本書が設計するのは 1 本目だけ**。

- **1 本目（本書の対象）**: skill を名指しで呼んだとき、調査を型どおり走り切れる
- **2 本目（別カード、本書の対象外）**: 名指しで呼ばなくても自然に効く。フェーズの振り分けへの追記、発火を狙った description の作り込み、作業の途中で作業クラスが調査に切り替わったことに何をもって気づくか、はすべてそちら

したがって本設計では、運用ルール（`.apm/instructions/main.instructions.md`）に手を入れない。

## 1. skill の名前と置き場所

- **名前**: `research-spike`
- **置き場所**: `.apm/skills/research-spike/SKILL.md`（配布側。スパイクは XP 由来の進め方の規律であり、痛みの一つは外部ツール調査で起きているため、利用者の環境でも同じ失敗が起きる）
- **改修者環境での認識**: `scripts/setup-dev.sh` が `.claude/skills/research-spike` への symlink を作る経路に載せる
- **frontmatter の `name`**: `research-spike`（ディレクトリ名と一致させる）

### 名前を `research-spike` にした根拠

公式の Skill authoring best practices の Naming conventions は、動名詞が先頭に来る形（`processing-pdfs`）を第一推奨とし、名詞句（`pdf-processing`）と動詞形（`process-pdfs`）を代替として認め、同時に「自分の skill 群の中で形を揃えること」を求めている。

xp-harness の既存 skill 名は名詞句と動詞形の混在（`basic-design` / `slice-tdd` / `story-slicing` / `define-requirements` / `git-workflow`）で、動名詞先頭形は無い。1 つだけ動名詞先頭形にすると群の中で揃わなくなるため、名詞句である `research-spike` を採る。この判断基準は改修者向けの `skill-design-style` skill に規約として書き足してある。

**却下した候補**:

- `spike`: 短く打ちやすいが、XP の語彙を知らない読み手には何の skill か伝わらない。1 本目は名指しで呼ぶ前提なので、打ったときに何の skill か分かることを優先した
- `investigation`: 分かりやすいが、使い捨て前提で小さく回すというスパイクのニュアンスが落ちる

## 2. 本文の章立て

調査そのものが一つの小さな一巡になっている、という捉え方を構造にする。**調査計画を出して合意するのは要件定義と基本設計をまとめた動きにあたり、実際に調べ出すのは実装にあたる。** したがって既にある対話モードと自走モードの境界が、調査の内側にもそのまま引ける。

並びは次のとおり:

```
なぜこの skill があるか
調査の計画を立てて依頼者と合意する   ← ここまで対話モード
調べる                               ← ここから自走モード
調べたことを計画に反映する
どこで終わるか
報告する
```

### 時系列で並べた根拠

読み手（エージェント）は調査の途中でこの skill を読み返すため、自分が今どこにいるかから引ける並びが要る。時系列以外の並べ方も検討した:

- **芯を軸に据える**（「意図を揃え、意図に届いたら終わる」を中心に置き、調べ方・記録・報告をぶら下げる）: 芯は冒頭に一度置けば足りるため、構造にする必要がない
- **防ぐ失敗から並べる**（早く閉じる・実況の地続き・引き継がれない、を先に挙げて拠り所を並べる）: 拠り所が失敗の裏返しでしか書けなくなる

**注意**: 時系列で並べることと、手順書にすることは別。要件定義の制約どおり、各章の中身は判断の拠り所として書き、番号付きの実行手順の列や条件分岐の羅列は持たせない。例外は報告の書式のみ（後述）。

## 3. 各章に何を書くか

### なぜこの skill があるか

調査は成果物が情報そのもので、次の判断・工程に渡って初めて価値になる。ストーリーと同じ型で扱うと「問いに答えた」で完了にしてしまう。この skill の核は「問いに答える」ではなく「判断の危険を潰す」。

### 調査の計画を立てて依頼者と合意する（対話モード）

書く拠り所:

- 何を決めるための調査か
- 何を確かめるつもりか
- **何が確かめられていれば、その判断をしてよいか**（＝完了の基準になる）
- 分かっていれば、この調査の結果を誰が使うか（分からなければ持ち越す。ここで止める条件にはしない）

計画は口頭で済ませず**ファイルに出す**（置き場所は後述）。理由は、エージェント一人の想像力で基準を決めさせないため。頭の中で意図を揃えても依頼者には見えないので、足しようがない。出し切ってから「他にありますか」を聞ける形にする。

**「壊れる道」という語彙は使わない**。元が既存ファイルの上書きという破壊事例なので、そこから抽象化した語が破壊の方に寄っている。判断が外れる形は破壊だけでなく、前提が違った・情報が古かった・規模が変わると成り立たない、も同じくらいある。守る側の言い方（何が確かめられていればこの判断をしてよいか）で書く。

**下調べは止めない**。既存の要件定義 skill は「調査（読む・探る、戻せる動き）はそのまま進めてよい」とモードのゲートを外しているが、そこには「どちらのモードでいくかを決めるための情報集めだから」という理由節が付いていて、指しているのは下調べ。本 skill が扱うのは、それ自体が成果物になる調査で別物。本文でこの切り分けを宣言し、既存の要件定義 skill には手を入れない。

### 調べる（自走モード）

書く拠り所:

- **反証で開く**: 裏付けを一つ取って閉じず、判断が外れる条件を確かめにいく
- **小さく速く回す**: 作り込まない、捨てる前提。**ミニマムな条件から始める**（最初から現実の散らかった状態でやると、何が効いたか切り分けられない）。利用者の現実の条件は、反証で当たりにいく対象の一つとして後から寄せる
- **事実と推測を分けて積む**: 観測と解釈を区別する。集計や自己報告を鵜呑みにしない
- **実験の場を実資産から隔離する**: 使い捨ての作業領域で試す。実データ・実環境を対象にする実験は依頼者の確認を取ってから行う

調べ方は 2 つに分ける。**情報取得型**（読む・探す。一次情報で裏を取る）と、**仮説検証型**（仮説を明示して試す）。単発の「動かして見てみる」も暗黙の仮説を持つので、仮説を明示させることに規律価値がある。

**実験の隔離を入れる理由**: この skill は「判断が外れる条件を確かめにいけ」＝壊れる方向を実際に試す方向にエージェントを促す。しかも配布されるので利用者の実プロジェクトで動く。不可逆な操作を止める規律を持つ配布 skill は実装フェーズのものだけで、調査では発火しない。

**ペアプロの相談相手**: 必要なときに呼ぶ道具として置く。「閉じる前に必ず呼ぶ」という手順にはしない（理由は「他の skill / subagent との繋ぎ」を参照）。

### 調べたことを計画に反映する

**記録用の別文書は作らない。調査計画のファイルに、分かったことを反映していく。**

この文書は、context が飛ばないようにするためのメモであって、人に見せるものではない。人に見せるのは最後の報告だけ。

この形にする利点が 2 つある。人に見せるための整形が要らない。そして、計画に書いた「これが確かめられていれば判断してよい」の横に分かったことが並ぶので、**終わっているかどうかが見て分かる**。

会話の順に追記していく形は避ける（過去の調査で、記録が報告の控えになって用語が割れた）。計画に反映していく形にすれば、論点ごとに区切られて上書きされるので、自動的にそうなる。

### どこで終わるか

終わりは 2 通り。どちらも出口は同じで、依頼者への報告に出る。

- **合意した意図を達成できる状態に到達した**
- **達成できないと分かった**（判断そのものが成り立たない、前提が違った、など）。前提を変えるところから議論が要るので、報告して依頼者に返す

この形にすると完了の基準が入口で外から与えられるため、調査する本人が基準を作って本人が完了を押す構造にならない。

### 報告する

**この章だけは具体的な書式を書く**（他の章は判断の拠り所として書く）。理由は、報告が実況の地続きになって結論に届かない、という失敗が実際に起きているため。公式の指針も、応答が長くなりがち・実況しがちなので長さと伝え方は明示的に指示せよと言っている。

書式:

- 実況と報告を地続きにしない。はっきりした区切りを立てて「ここから報告」
- 最抽象の結論から。問いへの答え、平易な意味、確信の温度感（どこまで調べ切ったかの厚み、残リスクを含む）
- 抽象度を上から下へ。結論 → 詳細（何をどう調べたか）→ 証拠（生データで裏を取ったものだけ）
- 提案は軽く、確定しない。次の一手は出すが判断は依頼者に残す

報告を出した後、**書き起こすかどうかと、誰向けかを依頼者に確認する**。誰向けか分からないと引き継ぎ文書は書けない。作ると決まったら、引き継ぎ文書を書く skill（`handoff-docs`）を呼ぶ。

## 4. 他の skill / subagent との繋ぎ

出口には 2 つある。**依頼者への報告**と、**次に使う人への引き継ぎ文書**。これを分ける。

- **報告**: いつも出す。書式は本文が持つ
- **引き継ぎ文書**: 使う人がいるときだけ作る。中身の規律は持たず、`handoff-docs` skill を呼ぶだけ

| 繋ぎ先 | いつ | 本文での扱い |
|---|---|---|
| `handoff-docs` skill | 報告の後、書き起こすと決まったとき | 呼ぶ（中身は持たない） |
| ペアプロの相談相手（reviewer 系 subagent） | 必要と判断したとき | 呼べることだけ書く。手順化しない |

### 検証・再点検を指示する文言を入れない、ただし接続動線は別

要件定義の制約に「検証させる指示・自分の仕事を再点検させる指示・確認用に subagent を呼ばせる指示は入れない」がある（公式の Opus 5 向け指針。モデルが元々やることと重なって過剰になる）。

**この制約が掛かるのは「同じ主体にもう一度やらせる指示」まで。別の主体に渡す接続動線（別 skill / 別 subagent を呼ぶ）は対象外**とする。この線を引かないと、引き継ぎ文書の skill を呼ぶ動線まで禁じられ、引き継ぎが落ちるという元の痛みが塞げなくなる。

判断の分かれ目は「同じ主体にもう一度やらせるか / 別の主体に渡すか」。

ペアプロの相談相手を手順化しないのはこの制約の側にあたる。枠が狭いことは自己点検では出てこないので道具としては残すが、「閉じる前に必ず呼ぶ」と書くと過剰になる。

## 5. 調査計画ファイルの置き場所

- **置き場所**: `docs/working/<題名>/` 配下（既存の要件定義・基本設計と同じ場所）
- **ファイル名**: `調査計画.md`
- **性質**: context を保つためのメモ。人に見せるものではない。調べながら更新していく

要件定義では「調査記録の置き場所」として未決にしていたが、記録用の別文書を作らず調査計画のファイルに反映していく形に決まったため、置き場所の問題は調査計画ファイルの置き場所に一本化された。

## 6. 既存資産への影響

- **`.apm/skills/research-spike/SKILL.md`**: 新規作成
- **`.claude/skills/research-spike`**: symlink 追加（`scripts/setup-dev.sh` の対象に載せる）
- **`.apm/instructions/main.instructions.md`**: **変更しない**（フェーズの振り分けへの追記は 2 本目のストーリー）
- **`.apm/skills/define-requirements/SKILL.md`**: **変更しない**（既存の「調査は止めない」が指すのは下調べで、本 skill が扱う調査とは別物。切り分けは本 skill の本文側で宣言する）
- **`.claude/skills/harness-verification/SKILL.md`**: **今回は変更しない**。報告の書式と反証可能性の規律が重複するが、重複許容で開始する方針（要件定義の決定）。本文を書いた後に突き合わせる
- **`kanban/TODO_tier1_調査スパイクskill新設.md`**: 2 本目のストーリー用のカードを別途切る（未着手）

### 集約するときに取れる形は対称ではない

照合の相手である `harness-verification` は非配布（改修者向けに直接コミット）、本 skill は配布側。**非配布から配布への参照は成立するが、配布から非配布への参照は利用者の環境に参照先が無く壊れる**。照合の段でこの向きの制約を踏まえる。

## 8. まだ決まっていないこと

- **description の文面**: 本文を書いてから、その中身を抽象化して起こす。先に文面を決めると、本文と食い違うか、本文を文面に合わせて歪めることになる。なお発火精度の作り込みは 2 本目のストーリーの範囲で、1 本目では責務が宣言できていれば足りる
- **`harness-verification` との重複をどうするか**: 重複許容で開始し、本文を書いた後に突き合わせる（意図的な先送り。書く前に集約構造を決めるのは抽象化の先払いで、書いてみたら検証固有・調査固有で内容が割れる可能性がある）

## 9. 実装フェーズで踏まないための注記

- **`.apm/` 配下の配布物に触れるため、main へ直接統合しない**。branch を push して PR を出す（改修者向け CLAUDE.md の Git 運用の上書きルール）
- **`handoff-docs` skill は現状 `.claude/skills/` に symlink されておらず、この環境では skill として発火しない**。本文から呼ぶ設計にはするが、改修者環境で動作を確かめるには symlink の追加が要る（`scripts/setup-dev.sh` の対象を確認する）
