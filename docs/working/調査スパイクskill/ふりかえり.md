# 調査スパイクskill ふりかえり

## 2026-08-06: 本番セッション分析から入口改修・再現ラン検証・v0.18.0 リリースまで

### サマリ

実プロジェクトで体感「全然ダメ」だった `research-spike` のセッションを transcript で分析し、入口を組み替え、同じ依頼文の再現ランで効果を確認して v0.18.0 としてリリースした一連のセッションのふりかえり。**分析対象のセッションと同じ失敗を、分析している自分がやっていた** — 規律が存在するのに、その規律を持つ skill を呼ばなかった。

### トピック一覧

よかった点:

- 分析を自己申告でなく生 transcript で裏取りした (「認識ずれてる」の 25 秒後に「合意できました」という決定的な 1 往復を拾えたのはそのため)
- 依頼者の案に根拠を持って反対した (`define-requirements` を呼ぶ案に対し、その skill 本文が調査を素通りさせる立場だと示した)
- `skill-reviewer` を 6 回呼び、複数回が本質的な取り違えを拾った (skill の核語を依頼者の言葉で上書きしていた件、README に「作業ディレクトリを書け」と開示規律に反することを書いた件、免除例が実測と矛盾する件)
- 公開のたびに `disclosure-auditor` を通した (FLAGGED を 1 回受けて置き場所ごと変えた)
- 自分の判定が違ったとき素直に取り下げた (`git-workflow` の割り込みを問題と決めつけた件)
- 書き戻し候補を実装する段で、候補の 2 件が既に本文にあることに気づいて「反映しない」と判断した (言われたとおり全部足すのでなく、重複を作らない側に倒した)

伸びしろ:

- **`harness-verification` skill を一度も呼ばなかった** (本番セッション分析のときと sandbox 再現ランのときの 2 回)。結果として記録の format 違反と、対話駆動の落とし穴 (`AskUserQuestion` への回答方法) を踏んだ。どちらも skill 本文に既に書かれていた
- **`git-workflow` skill を呼ばなかった**。セッション開始・コード変更・worktree 作成・commit・push と該当だらけなのに、description の「他より先に必ず最初に使う」が効いていない (途中の hook 通知でようやく呼んだ)
- **`dialogue-principles` を呼ばなかった**。設計対話が中心のセッションだった。しかも sandbox のエージェントには呼ばせておいて自分は呼んでいない
- **ツギハギに自分で気づかなかった**。入口を 3 ラウンド積み上げて 22 行 → 61 行にし、依頼者に「大丈夫？」と聞かれて初めて数えた
- **skill の核語を依頼者の言葉で上書きした**。依頼者が「なぜやるか」と言ったのをそのまま手順名にして、skill の責務を名指す「何を決めるための調査か」を消した (`skill-reviewer` が拾った)
- **宣言と結果が食い違った**。「main でそのまま」と言って送信したが、launcher の Enter が先頭候補を選び worktree が作られた
- **依頼者が remote control で並行操作していたことに気づかず**、途中から割り込む形でメッセージを送った
- **push が弾かれた直後に後片付けが走り、commit を落とした**。同じコマンド行に push と `worktree remove` を並べていた

取り決めへの書き戻し候補:

- `harness-verification` の `references/README.md` に、**本番の実運用セッションを分析した記録の「条件」の埋め方** (sandbox 前提のテンプレでは埋め方が自明でなかった) → 対応済み
- `harness-verification` 本文に、**照らす版を決める規律** (skill は改修で動くので、実走時に発火した版に照らす。ファイル側の現在版で照らすと実走時に無かった規律で判定する) → 対応済み
- `harness-verification` 本文に、**セッションが worktree に入ると transcript の置き場が変わる** (実際に見失った) → 対応済み
- `CLAUDE.md` に、**`harness-verification` を呼ぶ導線** (記載がゼロだった) → 対応済み
- `skill-design-style` の改修フローに、**効果を事実で確かめる手順** (手順 6 の `skill-reviewer` で終わっていた) → 対応済み
- `harness-verification` の description に、**対象として instruction** (skill / subagent だけだった) → 対応済み
- 検証記録を足したら validator を通す規律 → **既に本文にあった。反映しない**
- launcher の `AskUserQuestion` は矢印 + Enter で答える → **既に本文にあった。反映しない**
- `CLAUDE.md` に、短命な detached worktree に `setup-dev.sh` が要るかの線引き → **見送り** (実害が出ていない)

### 深掘り 1: harness-verification を 2 回とも呼ばなかった

#### 経緯

依頼は 2 段階だった。1 回目は「引き継ぎ書を読んで、本番セッションを分析して」。2 回目は「同じ条件で sandbox に流して確かめたい」。どちらも `harness-verification` の担当範囲そのもので、description の文言 (「本番の実運用セッションを『あるべき振る舞い』に照らして分析したいとき」) とほぼ一致していた。それでも一度も呼んでいない。

代わりに、同梱スクリプト (`setup-sandbox.sh` / `claude-launcher.sh` / `analyze-session.py`) を直接読んで回し、`references/` に記録を書いた。結果、記録が format 違反 (`## 結果` section の欠落) で validator に弾かれ、`AskUserQuestion` への回答方法を間違えて検証ランの選択が意図と違うものになった。**どちらも skill 本文に書かれていた** — 「足したら validator を通す」も「矢印 + Enter で答える、番号送信は誤爆する」も。

#### 分析

原因が 2 回で違う。

**1 回目は、発火判断そのものが起きていない。** 引き継ぎ書に的・分析のやり方・報告の形・スコープ境界が全部書いてあったので、文書に従って動いた。「この作業はどの skill の担当か」を一度も評価していない。皮肉なことに、この引き継ぎ書は `handoff-docs` の作法どおり「会話文脈ゼロで読める自己完結」に書かれている。**自己完結であるほど、その領域を持つ skill を締め出す**構造になっていた。

**2 回目は、周辺資産を読んだことによる充足感。** 検証だと自覚していた。スクリプトと `references/` を読んで回せてしまったので、skill の中身を持っている気になり、本文を読む動機が消えた。

そのうえで構造的な原因を調べたら、**`CLAUDE.md` に `harness-verification` の記載がゼロ**だった。名指しされている改修者向け skill / agent は `philosophy` / `release` / `skill-design-style` / `skill-reviewer` の 4 つだけで、スコープ境界の表にも載っていない。`skill-design-style` の改修フローにも出てこない (手順 6 の `skill-reviewer` で終わっている)。

同じセッション内に対照がある。

| skill | 常時 context の導線 | 改修フローの手順 | 発火 |
|---|---|---|---|
| `skill-design-style` | あり | — | 効いた |
| `skill-reviewer` | あり | 手順 6 | 6 回 |
| `release` | あり | — | 呼んだ |
| `harness-verification` | **なし** | **なし** | **0 回** |

導線がある skill は全部効き、無いものだけが落ちた。1 セッション内の自然実験になっている。

ただし**サボりの側面も認める**。2 回目は自覚があった。導線の不在と別に、本文を読まずに済ませた判断は私の怠りで、そこは構造のせいにしない。

#### アクション

- `CLAUDE.md` のスコープ境界の表に `.claude/skills/harness-verification/` を追加し、`skill-reviewer` の直後に呼ぶ導線の section を新設した。「同梱スクリプトだけを直接叩かない」も書いた (この規律は skill 本文には置けない — その経路では本文が読まれないため) → 対応済み
- `skill-design-style` の改修フローに手順 7「挙動に効く改修なら `harness-verification` で確かめる」を新設した。免除の輪郭は「文言を触ったか」でなく「読み手の判断材料が変わったか」で引いた (言い回しの整理を免除にすると、いちばん危ないカテゴリが免除の筆頭に来る。実測: `dialogue-principles` 旧 3/3・新 0/3 の回帰)。離脱の実経路は「重いので今回は省く」なので、呼ばない判断をしたら理由を依頼者に出す規律を添えた → 対応済み
- **この改修が効いたかは未検証**。改修者向けファイルは sandbox に deploy されないので sandbox で確かめられず、次に誰かが skill / instruction を改修するときにしか観測できない。狙って再現できないので、その機会に観測する

### 深掘り 2: ツギハギに自分で気づかなかった

#### 経緯

入口の改修を 3 ラウンド積んだ。1 ラウンド目で土台と見当を分け、2 ラウンド目で制約・既知事項・認識合わせを足し、3 ラウンド目で順序を入れた。各ラウンドで `skill-reviewer` に通し、指摘は毎回反映した。それでも依頼者から「FB を受けてツギハギになってない？」と聞かれるまで、自分では気づいていない。

数えたら入口 section は 22 行 → 61 行 (2.8 倍)。症状が 3 つあった。同じ 3 項目を 3 か所で書いていた。隣の文の誤読を先回りして塞ぐだけの文が 5 つ積み上がっていた。1 つの箇条書きに命令が 5 つ入っていた。

#### 分析

各ラウンドは局所的には正しかった。指摘は実在の穴を突いていて、対応も筋が通っている。問題は**指摘に 1 つずつ応じる構えが、全体の形を見る視点を持たない**こと。

`skill-reviewer` も同じ穴にはまっていた。毎回「この差分は妥当か」を見ていて、「積み上がった結果はどうか」を見ていない。3 ラウンド目のレビューでも肥大化の指摘は出ていない (行数が倍になったことは触れられたが、許容範囲と判断されていた)。

`skill-design-style` の手順 5「出力前に立ち止まる」は**1 回の出力**についての規律で、ラウンドをまたいだ累積には掛かっていない。累積を見る装置がどこにも無かった。

#### アクション

- 今回は依頼者の指摘で畳み直した (61 行 → 44 行、規律は落とさず)
- 装置としての手当ては**していない**。「N ラウンド積んだら全体を読み直す」のような規律を足すと、それ自体が手順の肥大化になる。累積を見る視点が要るという観測だけ残し、同じ痛みがもう一度出たら装置化を検討する

### 深掘り 3: skill の核語を依頼者の言葉で上書きした

#### 経緯

依頼者が理想の流れを言葉で示した。その 1 つ目が「なぜやるかがなければ理由を聞く」。私はこれをそのまま手順名にし、`research-spike` の手順 1 を「なぜやるかを聞く」と書いた。結果、skill の核語である「何を決めるための調査か」が本文から消えた。`skill-reviewer` が拾って戻した。

#### 分析

「なぜやるか」と「何を決めるための調査か」は近くて別物。前者は動機、後者は**守るべき判断対象の特定**。この skill が潰すのは「判断の危険」なので、判断対象が特定されないと確かめどころの的が立たない。description もその語で書かれていて、本文と description が繋がっていた。

なぜ気づかなかったか。**依頼者の言葉をそのまま使うのが忠実だと思っていた**。実際には、依頼者は「聞き方」を話していて、私は「本文が名指しする責務」を書いていた。層が違う。忠実さの向きを取り違えた。

`skill-design-style` の手順 5 には「既存例の見た目に引っ張られない。ルールが先、例は参考」とあるが、**依頼者の言葉に引っ張られない**は書かれていない。今回はそちらだった。

#### アクション

- 本文の語を戻し、聞き方は「問い方」の段落に分けた → 対応済み
- `skill-design-style` への書き戻しは**していない**。手順 5 に「依頼者の言葉に引っ張られない」を足す案はあるが、依頼者の言葉を尊重するのは基本の構えなので、否定形で書くと向きを外す危険がある。今回は `skill-reviewer` が拾えたので、その捕捉に委ねる
