# 調査スパイク skill 新設 — 要件定義

> このドキュメントは進行中の設計メモ。実装後もそのまま残す（振り返り・PR レビューで参照される）。
> 削除のタイミング・要否は依頼者または外側の仕組みで別途判断する（あなたは削除しない）。

## 1. 背景と動機

### 真の課題

要件定義・基本設計・実装にはフェーズ skill があるが、調査という作業クラスには持ち家が無い。そのため main session は調査をストーリーの型に流し込み、「問いに答える」をゴールに走ってしまう。

実害は 2 つのセッションで 3 つの形で顕在化した（詳細は `docs/working/AgentTeam調査スパイク/ふりかえり.md` 深掘り 1、`docs/working/Codex対応/ふりかえり.md` 深掘り 1・2）:

1. **完了の早すぎる宣言**: スパイクの Done を「問いに答えた」と固定し、「答えが次工程の入力として使える形で引き継がれている」まで含めなかった。AgentTeam 調査スパイク（2026-07-15〜16）で完了を 2 回早く宣言。引き継ぎ点検（handoff-verifier）は依頼者に促されて初めて実施した
2. **報告が実況の地続きで読みにくい**: 「検証するね → 生出力（巨大ダンプ）→ 解釈」を 1 メッセージに地続きで並べ、結論が冒頭に区切られず読み手が要点に届けない。AgentTeam 調査スパイクと Codex 対応セッション（2026-07-18、apm 挙動調査）の別々の調査で同じ痛みが 2 回出た
3. **調査の網羅性の片肺**: 「一つの肯定的な角度を裏付けたら閉じる」型で、判断が外れる条件を確かめにいかない。Codex 対応セッションで compile が既存ファイルを上書きするデータ破壊リスクを自力で拾えず、依頼者の反復質問で初めて発覚した

なお報告書式（実況と報告を分ける / 結論 → 詳細 → 証拠）と反証可能性の規律は `harness-verification` skill（改修者向け・非配布）に既に存在するが、発火条件が「xp-harness の skill / subagent の検証」に閉じており、一般の調査に効かなかった。「規律はあるのに一箇所に閉じて届かない」が構造的な根。

### この skill が守る価値

調査という作業クラスの型を配る。引き継ぎだけを守るのではない（調べ方が片肺なら引き継いでも意味がない）。

skill の核は「問いに答える」ではなく「**判断の危険を潰す**」に据える。

## 2. 位置づけ — 実装フェーズ skill と同格のフェーズ skill

この skill は横断的な補助 skill ではなく、**作業クラスが「調査」のときの実行フェーズ skill**。要件定義には要件定義の skill、実装には実装の skill があるのと同じ並びで、調査には本 skill が対応する。

- 実装フェーズの skill が「どう TDD で回してどう成果を届けるか」を持つのと同型で、本 skill は「どう調査を回してどう知見を届けるか」を持つ。やることが実装か調査かの違いだけで、レイヤーは同じ
- 呼ばれ方はフェーズの振り分けと同じ場所。依頼冒頭のフェーズ判定と、運用ルールの「フェーズと skill」の並びに「調査 → 本 skill」として載る。**運用ルール（main instruction）の変更がスコープに入る**
- 実装 skill の本文から呼ぶ形は採らない（却下理由: 実装フェーズに入っている時点で作業クラスの判定は済んでおり、構造として遅い。実装 skill は自走モードの skill なので、そこから調査 skill に入るのは導線として合わない）

## 3. 理想の調査 — 入口 / 最中 / 出口

### 入口 — 調査として立ち上がっているものに絞る

**対象は「調査として立ち上がっている作業」**。カード化された独立スパイク、依頼として来る調査、セッションの主題が調査であるもの。

**実装を進めている最中にぬるっと生えた調べ物は、当面スコープ外**（後述のスコープ外を参照）。

芯は **意図の共有**。何を決めるための調査か、何が確かめられていればその判断をしてよいか。これが揃っていれば、調査中に新しく見えた確かめどころも、本人が自分の潰すべきものかどうか判断できる。

**採らなかった形**: 「判断が壊れる道を開始時に列挙し、各モードを反証し、全部潰れたら完了」という装置。理由は 2 つ。列挙するのが調査する本人なので、枠が狭いままでも自分で完了の印を押せる（Codex 対応で実際に起きた「一つの角度を裏付けて閉じる」がそのまま通ってしまう）。そして根本原因はふりかえりが「起点に『何を決めるための調査か』を置いていない」と書いており、意図の欠落であって手続きの欠落ではない。手続きを一枚足すより意図を揃える方が根に近い。

**言葉の置き方**: 「壊れる道」という語彙は使わない。元が compile の上書きという実際の破壊事例で、そこから抽象化したため破壊の方に寄っている。判断が外れる形は破壊だけでなく、前提が違った・情報が古かった・規模が変わると成り立たない、も同じくらいある。守る側の言い方（**何が確かめられていればこの判断をしてよいか**）に寄せる。

### 最中

- **反証で開く**: 裏付け一発で閉じず、判断が外れる条件を確かめにいく
- **小さく速く回す**: 小さい実験の繰り返し。作り込まない、捨てる前提。**ミニマムな条件から始めるのが既定**（最初から現実の散らかった状態でやると何が効いたか切り分けられない）。利用者の現実の条件は、反証で当たりにいく対象の一つとして後から寄せる
- **事実と推測を分けて積む**: 観測と解釈を区別する。集計や自己報告を鵜呑みにしない

調べ方は 2 つに分ける:

- **情報取得型**: 読む・探す。一次情報で裏を取る
- **仮説検証型**: 仮説を明示して試す。実験・観測はこのループの中の動作

単発の「動かして見てみる」も暗黙の仮説を持つ。仮説を明示させることに規律価値がある（Codex 対応の痛みは「問題ないだろう」という暗黙の仮説を明示しなかったため反証に行けなかった）。

**ペアプロの相談相手**: 必要なときに呼ぶ道具として置く。「閉じる前に必ず呼ぶ」という手順にはしない（理由は制約の項を参照）。

### 出口 — 依頼者への報告と次工程への引き継ぎ

出口は 2 通りありうる（エージェントがそのまま知見を使って進む / 依頼者に報告して判断を仰ぐ）が、**エージェント自走消費のケースはスコープ外**とし、依頼者への報告と次工程への引き継ぎに絞る。

理由: 記録に残る痛み 3 件の出口はすべて「知見が依頼者の判断・次工程に渡る」側で、自走消費側で顕在化した痛みは無い。自走中の小さい調べ物は「その場で消費される調べ物は対象外」で既に除外済み。それより大きい自走中の迷いは実装 skill の止まる / 進む判断軸が既に統べている。痛みが顕在化していないところに装置を作らない。

**書式は検証レポートの調査版**:

- 実況と報告を地続きにしない。はっきりした区切りを立てて「ここから報告」
- 最抽象の結論から。問いへの答え + 平易な意味 + 確信の温度感（どこまで調べ切ったかの厚み、残リスクを含む）
- 抽象度を上から下へ。結論 → 詳細（何をどう調べたか）→ 証拠（生データで裏を取ったものだけ）
- 提案は軽く、確定しない。次の一手は出すが判断は依頼者に残す

出典は `.claude/skills/harness-verification/SKILL.md` の「報告は『検証レポート』の書式で出す」section。重複照合の第一候補。

## 4. ユーザーストーリー

- **xp-harness の利用者（開発チーム）** が、**調査の成果を次の判断・工程に安心して使えるようにするために**、**エージェントが調査を、意図を揃えてから反証で開き、読める形で引き継ぐところまで走り切れるようにしたい**

補足: 改修者も self-host（dogfooding）で同じ恩恵を受ける。

## 5. Done（完了基準）

- **配布側に skill が存在する**: `.apm/skills/` 配下に SKILL.md があり、改修者環境でも発火可能な経路（symlink）に載っている
- **description が「調査として立ち上がっている作業」を発火条件として宣言している**: skill-design-style の規律準拠（third person / What+When / 抽象表現）
- **フェーズの振り分けに載っている**: 運用ルールの「フェーズと skill」に調査フェーズとして追記されている
- **本文が入口・最中・出口の拠り所を持つ**:
  - 入口 — 何を決めるための調査か、何が確かめられていればその判断をしてよいか
  - 最中 — 反証で開く / ミニマムから小さく速く回す / 事実と推測を分けて積む
  - 出口 — 実況と報告を分ける、結論 → 詳細 → 証拠、引き継ぎとして仕上げる
- **本文が手順書になっていない**: 手順の書き下しではなく判断の拠り所として書かれている（制約の項を参照）
- **harness-verification との重複照合の判断が記録されている**: 新 skill を書いた後に報告書式・反証可能性の規律と突き合わせ、同内容なら集約、割れるなら重複維持を判断し、結果を `docs/working/調査スパイクskill/基本設計.md` に残す
- **skill-reviewer のレビューを通過している**

## 6. スコープ外

- **実装を進めている最中に生えた調べ物**: 作業クラスが実装から調査に切り替わったことに何をもって気づくかという別問題を抱えており、既存のフェーズ判定の導線が届かない。ここを支えるかどうか自体が判断事項で、まだ痛みが記録に無いため当面外す。記録に残る痛み 3 件は、いずれも調査として立ち上がっている作業の中で起きているため、絞っても射程は落ちない
- **エージェント自走消費の出口**: 上記の出口の項の理由による
- **運用ルールの仮置き芯（「新しいライブラリ・ツールは思想を調べてから使う」）の移設**: skill 発火前に効くべき規律（まだ調査の必要性に気づいていない瞬間に効く）なので、発火後に読まれる skill 本文へは移さない
- **retrospective skill の裏取り条項拡張**: 同じふりかえりから出た別アクション。別カードで扱う
- **harness-verification の検証固有規律の改修**: 照合の対象は報告書式・反証可能性の汎用部分のみ
- **handoff-docs / handoff-verifier 自体の改修**: 新 skill から呼んで接続するだけで、両者の中身は変えない
- **新 skill の発火率・振る舞いの検証**: 事後評価に委ねる（harness 機構の E2E テスト枠組み未確立の方針どおり、事前縛り最小化・事後評価許容）

## 7. 制約（Constraints）

- **本文は手順を持たず、判断の拠り所だけ持つ薄いものにする**: 調査は高性能モデルが担う前提。公式の推奨は「手順を書き下すより一般的な指示の方がよい（モデルの推論は人が書く手順を上回ることが多い）」「賢いモデルほど細かい指示を必要としない」。ただし逆に薄すぎる指示（抽象的な方針だけで具体的な手がかりを与えない、共有前提を勝手に仮定する）も同じく失敗すると明記されており、狙うのは中間。出典: [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) / [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **検証・再点検を指示する文言を本文に入れない**: 公式の Opus 5 向け指針に「検証させる指示・自分の仕事を再点検させる指示・確認用に subagent を呼ばせる指示は外せ。モデルが元々やることと重なって過剰になり、コストだけ増えて質は上がらない」とある。ペアプロの相談相手は、枠の狭さという自己点検では出てこないものに当てる道具として残すが、手順化せず必要なときに呼ぶ形にする。出典: [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- **ただし報告の書式は例外として具体的に書く**: 上の 2 つの制約は「調べ方の手順」と「検証の指示」に掛かるもので、**出力の書式には掛からない**。同じ Opus 5 向け指針は逆に、応答が長くなりがち・実況しがちなので、長さと伝え方は明示的に指示せよと言っている。記録に残る痛みの 2 つ目（実況の地続き・結論が冒頭に来ない）はまさにこの失敗なので、出口の書式（区切りを立てる / 結論 → 詳細 → 証拠 / 確信の温度感）は薄くせず具体的に書く
- **上記の出典は system prompt を対象にした指針である点に注意**: 本 skill の本文は、system prompt・プロジェクトの運用ルール・他 skill が既に載った状態の agent に、発火時に追加で読み込まれるもので、消費のされ方が違う。それでも「賢いモデルには手順でなく判断の拠り所を渡す」という芯は同じ理由で効くと判断して制約に採用しているが、基本設計で過剰に一般化しないこと
- **組織ルール: skill-design-style の規律に従う** — 2 層構造（frontmatter = interface / 本文 = 実装）、境界原則（description は interface / 本文は展開後も自然 / 発火条件と振る舞いを混ぜない）、name フィールドの明示（name = ディレクトリ名）
- **組織ルール: 配布物としての表現制約** — 本文に APM 機構固有の語彙を持ち込まず、consumer の環境に展開された状態で自然に読めること。既存配布 skill に合わせ日本語で書く
- **組織ルール: 統合は PR 経由** — `.apm/` 配下の配布物に触れる変更なので main へ直接統合しない
- **組織ルール: 外部 OSS の固有名詞を成果物に書かない** — 着想元があっても名前は残さない

## 8. まだ決まっていないこと

- **止まり方**: どこで調査を完了とするか。「列挙が全部潰れたら完了」という形を採らないと決めたため、代わりの拠り所が空いている
- **始め方の合意主体**: 調査の意図と見立てを依頼者と合意してから進むのか、宣言して進むのか
- **調査記録の置き場所**: skill が置き場所の規約を持ち、具体パスは基本設計で決める方向
- **検証 skill との重複の扱い**: 重複許容で開始し、書いた後に照合する（下記の決定の経緯を参照）

## 決定の経緯（却下案・保留判断）

- **責務境界（配布するか）**: 配布側 `.apm/skills/` と決定。スパイクは XP 由来の進め方の規律（中身の流儀ではない）で、痛みの 1 つは外部ツール調査で起きており consumer 環境でも同じ失敗が起きる構図のため。「まず改修者向けで熟してから配布」案は採らなかった
- **報告書式・反証可能性の集約方式**: 「新 skill に集約して harness-verification から呼ぶ」「重複許容」「第三の共通 skill 切り出し」を比較し、**重複許容で開始**と決定（依頼者判断）。理由: 書く前に集約構造を決めるのは抽象化の先払いで、書いてみたら検証固有・調査固有で内容が割れる可能性がある
- **判断が外れる条件の列挙を装置として持つ案**: 却下。理由は入口の項に記載
- **現実の初期状態で試すことを最中の独立項目に置く案**: 却下。反証の対象の一つに吸収し、既定はミニマムから始める形にした。原因の切り分けができなくなるため
- **閉じる前にペアプロの相談相手を必ず呼ぶ案**: 却下。公式の指針と正面から当たる（制約の項を参照）
- **運用ルールの仮置き芯の移設**: 一度「今回含める」と合意した後、依頼者の指摘で覆してスコープ外に
- **handoff-docs の description に「調査記録」を例示追加する案**: 却下（AgentTeam 調査スパイクふりかえりで棄却済み）。例示リストの増殖は「例示に無いものは対象外」の読みを強化するため筋が悪い
