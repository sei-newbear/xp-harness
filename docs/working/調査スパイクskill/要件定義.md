# 調査スパイク skill 新設 — 要件定義

> このドキュメントは進行中の設計メモ。実装後もそのまま残す（振り返り・PR レビューで参照される）。
> 削除のタイミング・要否は依頼者または外側の仕組みで別途判断する（あなたは削除しない）。

## 1. 背景と動機

### 真の課題

要件定義・基本設計・実装にはフェーズ skill があるが、調査/スパイクという作業クラスには持ち家が無い。そのため main session は調査をストーリーの型に流し込み、「問いに答える」をゴールに走ってしまう。

実害は 2 つのセッションで 3 つの形で顕在化した（詳細は `docs/working/AgentTeam調査スパイク/ふりかえり.md` 深掘り 1、`docs/working/Codex対応/ふりかえり.md` 深掘り 1・2）:

1. **完了の早すぎる宣言**: スパイクの Done を「問いに答えた」と固定し、「答えが次工程の入力として使える形で引き継がれている」まで含めなかった。AgentTeam 調査スパイク（2026-07-15〜16）で完了を 2 回早く宣言。引き継ぎ点検（handoff-verifier）は依頼者に促されて初めて実施した
2. **報告が実況の地続きで読みにくい**: 「検証するね → 生出力（巨大ダンプ）→ 解釈」を 1 メッセージに地続きで並べ、結論が冒頭に区切られず読み手が要点に届けない。AgentTeam 調査スパイクと Codex 対応セッション（2026-07-18、apm 挙動調査）の別々の調査で同じ痛みが 2 回出た
3. **調査の網羅性の片肺**: 「一つの肯定的な角度を裏付けたら閉じる」型で、「判断が壊れる道」（失敗モード・壊す方の副作用・利用者の現実の初期状態）を反証しにいかない。Codex 対応セッションで compile が既存ファイルを上書きするデータ破壊リスクを自力で拾えず、依頼者の反復質問で初めて発覚した

なお報告書式（実況と報告を分ける / 結論 → 詳細 → 証拠）と反証可能性の規律は `harness-verification` skill（改修者向け・非配布）に既に存在するが、発火条件が「xp-harness の skill / subagent の検証」に閉じており、一般の調査に効かなかった。「規律はあるのに一箇所に閉じて届かない」が構造的な根。

### この skill が守る価値

調査という作業クラスの**全工程の型**を配る。引き継ぎだけを守るのではない（調べ方が片肺なら引き継いでも意味がない）:

- **始め方**: どの判断のための調査か、その判断が壊れる道の列挙、出力の宛先、引き継ぎまで含む Done の設定
- **調べ方**: 裏付けで閉じず反証で開く、利用者の現実の初期状態を再現する
- **残し方**: 実況と報告を分ける、結論 → 詳細 → 証拠の書式、用語の固定
- **仕上げ**: 引き継ぎ文書として仕上げ、文脈ゼロ点検を通してから完了を宣言する

skill の核は「問いに答える」ではなく「**判断の危険を潰す**」に据える。

### 発火の輪郭 — XP のスパイクのノリ

発火条件の錨は XP のスパイク: **ある問いに答えるための、使い捨て前提の小さな実験・調査**。ストーリーの見積もりや設計判断を阻む不確実性を潰すために行い、成果物は動くコードではなく知見。

- **発火する**: 「この問いを潰さないと次の判断・見積もりができない」不確実性を潰しにいく作業。カード化された独立スパイクも、ストーリー進行中に「これは一度実験しないと分からない」と切り出す場面も、同じノリで対象（Codex 対応セッションの apm 調査は後者 — 途中で発生した計画外のスパイクを、スパイクと認識せず流し込んだ失敗例）
- **発火しない**: 実装の手を動かす流れの中でその場で消費される調べ物（API の使い方確認など）。切り出す動機がないもの

## 2. ユーザーストーリー

- **xp-harness の利用者（開発チーム）** が、**調査の成果を次の判断・工程に安心して使えるようにするために**、**エージェントが調査を XP スパイクの型 — 始め方・調べ方・残し方・仕上げ — で走り切れるようにしたい**

補足: 改修者も self-host（dogfooding）で同じ恩恵を受ける。

## 3. Done（完了基準）

- **配布側に skill が存在する**: `.apm/skills/` 配下に SKILL.md があり、改修者環境でも発火可能な経路（symlink）に載っている
- **description が「XP スパイクとして切り出す作業」を発火条件として宣言している**: skill-design-style の規律準拠（third person / What+When / 抽象表現）
- **本文がスパイクの全工程の規律を持つ**:
  - 始め方 — どの判断のための調査か、判断が壊れる道の列挙、出力の宛先、引き継ぎまで含む Done の設定
  - 調べ方 — 裏付けで閉じず反証で開く、利用者の現実の初期状態を再現する
  - 残し方 — 実況と報告を分ける、結論 → 詳細 → 証拠、用語の固定
  - 仕上げ — 引き継ぎ文書として仕上げ、文脈ゼロ点検を通してから完了を宣言する
- **harness-verification との重複照合の判断が記録されている**: 新 skill を書いた後に harness-verification の報告書式・反証可能性の規律と突き合わせ、同内容なら集約、割れるなら重複維持を判断し、その結果を docs/working の文書に残す
- **skill-reviewer のレビューを通過している**

## 4. スコープ外

- **main.instructions.md の仮置き芯（「新しいライブラリ・ツールは思想を調べてから使う」）の移設**: skill 発火前に効くべき規律（まだ調査の必要性に気づいていない瞬間に効く）なので、発火後に読まれる skill 本文へは移さない。扱いは main-instructions 再構成側で別途判断
- **retrospective skill の裏取り条項拡張**: 同じふりかえり（AgentTeam 調査スパイク）から出た別アクション。別カードで扱う
- **harness-verification の検証固有規律の改修**: 照合の対象は報告書式・反証可能性の汎用部分のみ。検証固有の中身（transcript の読み方等）には触れない
- **handoff-docs / handoff-verifier 自体の改修**: 新 skill から呼んで接続するだけで、両者の中身は変えない
- **新 skill の発火率・振る舞いの検証**: harness-verification による事後評価に委ね、本カードの完了条件には含めない（harness 機構の E2E テスト枠組み未確立の方針どおり、事前縛り最小化・事後評価許容）

## 5. 制約（Constraints）

- **組織ルール: skill-design-style の規律に従う** — 2 層構造（frontmatter = interface / 本文 = 実装）、境界原則（description は interface / 本文は展開後も自然 / 発火条件と振る舞いを混ぜない）、name フィールドの明示（name = ディレクトリ名。cross-agent 配布先で必須）
- **組織ルール: 配布物としての表現制約** — 本文に APM 機構固有の語彙（`.apm/` パス、compile 等）を持ち込まず、consumer の環境に展開された状態で自然に読めること。既存配布 skill に合わせ日本語で書く
- **組織ルール: 統合は PR 経由** — `.apm/` 配下の配布物に触れる変更なので main へ直接統合しない（改修者向け CLAUDE.md の git-workflow 上書きルール）
- **組織ルール: 外部 OSS の固有名詞を成果物に書かない** — 着想元があっても名前は残さない

## 決定の経緯（却下案・保留判断）

- **責務境界（配布するか）**: 配布側 `.apm/skills/` と決定。スパイクは XP 由来の進め方の規律（中身の流儀ではない）で、痛みの 1 つは外部ツール調査で起きており consumer 環境でも同じ失敗が起きる構図のため。「まず改修者向けで熟してから配布」案は採らなかった
- **報告書式・反証可能性の集約方式**: 「新 skill に集約して harness-verification から呼ぶ」「重複許容」「第三の共通 skill 切り出し」を比較し、**重複許容で開始**と決定（依頼者判断）。理由: 書く前に集約構造を決めるのは抽象化の先払いで、書いてみたら検証固有・調査固有で内容が割れる可能性がある。新 skill を書いた後に突き合わせ、同内容ならその時点で切り出す（Done の「重複照合の判断の記録」がこれを担保）
- **instruction の仮置き芯の移設**: 一度「今回含める」と合意した後、**依頼者の指摘で覆してスコープ外に**。「新ツールの思想を調べてから使う」が効くべき瞬間は skill 発火前（調査の必要性にまだ気づいていない瞬間）で、発火後に読まれる本文へ移すと守りが消えるため。skill-design-style の境界原則「発火前に効く話は description / 常時 context、発火後に効く話は本文」と整合
- **handoff-docs の description に「調査記録」を例示追加する案**: 却下（AgentTeam 調査スパイクふりかえりで棄却済み）。例示リストの増殖は「例示に無いものは対象外」の読みを強化するため筋が悪い
